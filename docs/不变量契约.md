# 不变量契约

这个项目有一类 bug 反复出现：**常规路径完全正常，只在边缘悄悄坏掉，而且不报错**——
`latest.json` 漏改让更新横幅静默失效 9 个版本；跨 IPC 传响应式对象报错被 Vue 吞掉，
表现为「状态改了、盘上没写」；取消「印」之后模板字段静默消失、打出白版。

逐个案例打补丁（每出一次 bug 加一条静态守卫）永远慢 bug 一步。这份清单换一种做法：
把**必须永远成立**的条件显式命名，每条都指向一个测试文件里守它的锚点，
再由 `test/invariants.cjs` 机器校验「锚点还在、套件还挂在 `npm test` 里」。

> 加新守卫时：在这里登记一条 `### I-XX`，并在 `test/invariants.cjs` 的 `CONTRACT`
> 里补上对应的 `{ file, anchor }`。契约测试会红，直到两边对齐——
> 这就是「先声明再守卫」，而不是「追着 bug 跑」。

### I-01 存储通道只放行 UI 偏好类

`store:load` / `store:save` 的白名单**显式列举** `settings`、`display-settings` 两个键，
不用「文件名形状」校验。形状校验挡不住 `datasets` / `templates` 这类领域库——
一行调用就能清空用户全部数据。唯一权威源在 `electron/api.cjs`，`ipc.cjs` 不自持副本。

### I-02 外部链接协议白名单

只放行 `https:`。`http` / `file:` / `smb:` / `javascript:` / `data:` / `vbscript:` 一律拒绝——
`file:` 能拉起本地 exe，`smb:` 在 Windows 上会触发 NTLM 协商。`parseInfo` 必须把非法 url
抹成空串，而不是原样透传给渲染层。

### I-03 新窗口默认 deny

`setWindowOpenHandler` 所有路径最终都返回 `deny`，只把 `https` 交给系统浏览器。
旧代码 default 就是 allow，等于把新窗口的处置权交给了页面。

### I-04 文件名消毒并真的接线

模板名会直接拼进 `defaultPath`，必须过 `sanitizeFilename`：清路径非法字符、控制字符、
首尾空白与结尾点，改写 Windows 保留设备名（CON/PRN/AUX/NUL/COM1/LPT9），限长 80。
关键是**接线**——实现存在但零调用等于没有。

### I-05 底图格式按内容判定

拖拽 / 剪贴板只有字节、没有可信文件名，格式必须按内容嗅探：内容是 PNG 却叫 `.jpg`
也存成 `.png`；内容不是图片、即使叫 `.png` 也拒绝；只取 basename，挡住路径穿越。

### I-06 底图文件与模板记录解耦

底图文件的生死只看「用户还要不要它」：换图 / 删图当场删（`discardBackground`），
**不跟保存绑定**、**不进撤销栈**（文件已删，撤销回来只会是张破图）。路径来自可手工编辑的
JSON，越界路径必须被守卫挡下。

### I-07 取消「印」使模板字段失效

模板字段引用的列一旦被取消「印」（`printOn=false`），校验必须判为缺失并**阻断放行**
（原因 `not-printable`），否则会照常出片、印出空白。

### I-08 0 份出片不得计「已打」

`shouldMarkPrinted`：空数据集（0/0）或勾选 0 条（partial）都不回写「已打」——
不能让空数据集凭空多出一个成功信号。

### I-09 缓存清理结果必须上报

「清理缓存」不能静默：删不掉的（运行中的 `GPUCache`/`DawnCache` 必 EPERM）要记进
`failed` 并排队到下次启动，界面必须如实说「已清理多少」/「正被占用，下次启动清理」，
不许出现「点了没反应」。清理必须排在 `app.whenReady()` **之前**（晚了 GPU 进程已持有目录）。

### I-10 隐藏 ≠ 取消「印」

数据页隐藏一列只影响**表格渲染**；模板字段面板 / 打印前校验 / 出片一律只看 `printOn`。
两者一耦合，用户隐藏一列就会让模板字段静默消失、打出白版。另外：至少留一列、
`#` 与「操作」列不可藏、按 `col.key` 记、补录跳转撞上隐藏列要自动展开。

### I-11 跨 IPC 传参必须纯对象

`ref({})` 里装的是 Vue 响应式 Proxy，而 IPC 走结构化克隆，**同步**抛
`An object could not be cloned.`，又会被 Vue 的事件处理吞掉 ⇒ 表现成「状态改了、盘上没写」，
同一次操作里它后面的语句还全不执行。一律先 `JSON.parse(JSON.stringify(x))`。

### I-12 display-settings 是整写镜像

内存里只有 `tableSize` + `hiddenColumns`，每次**整写**（不是读-改-写）。读-改-写在两次
快速操作下会交错（先点字号再隐藏列，后写的丢掉前一次）。两个前置守卫别动：
没读到落盘值之前不许写、写盘前必须转纯对象。

### I-13 落盘偏好在 setup 阶段就读

补录跳转靠 `watch(cellNav.req, { immediate: true })`，它在 setup 阶段就跑，要读隐藏状态
判断「目标列是否被藏」。挂 `onMounted` 里读就晚了——读到空 map ⇒ 自动展开失效，
反向还会用旧值盖掉刚写下去的状态。

### I-14 徽标不许被拆成两行

`.det-flag` 等状态徽标一律 `white-space: nowrap` + `display: inline-block`。
表格 auto layout 按 min-content 分配列宽，中文徽标可断字 ⇒ 窗口非最大化 + 方式列被
「导出 PDF 部分 5/7」撑开时，「完成」会被压成「完」/「成」两行。

### I-15 打印出口失败必须留痕

`print:send` / `print:exportPdf` 失败时也要写 `failed` 留痕（在 `return` 之前），
两个出口对称——失败不能只在界面上闪一下、历史里查不到。

### I-16 多选对齐把盒边缘换算回锚点

对齐目标是像素位置，而 `f.x` 是锚点百分比，写入前必须按 `anchorRatio` 换算
（推导见 `src/lib/field-edit.cjs` 的 `alignedX`/`alignedY`）。漏掉换算会让非居中字段
整体偏 `(0.5−r)×盒宽`，之后拖动时吸附起点随之错位。

### I-17 清空尺寸不被静默锁死

成品尺寸输入：空值 / 非法值 / ≤0 一律**不写回**（`clampItemDim` 返回 `null`）。
原来是 `Number('')→0→钳到 5`，用户想清空重输，结果被静默锁成 5mm——用户还没输完就被改掉值，
比不接受输入更糟。

### I-18 api.cjs 零 electron 依赖

`electron/api.cjs` 是 agent 接口与 GUI 通道的共同地基，**不得** `require('electron')`，
也不得 `require('./printer.cjs')`（后者 require electron，会污染整条依赖链）。
一旦破坏，CLI 立刻崩，而 GUI 毫无察觉。

### I-19 画布字段框的盒宽必须等于文字宽

用户报「模板排版的预览页里字段位置和导出的 PDF 不一致，导出会往右漂移一点点」。

根因不在渲染引擎：画布与出片**都靠「盒宽 × `anchorRatio`」算 `translateX` 位移**
（center→−50% / right→−100% / left→0），所以画布盒宽必须恰好等于文字宽，
多出来的每一像素都直接变成出片位置漂移。历史踩过两次：

| 属性 | 后果 | 实测偏差（A4） |
|---|---|---|
| `padding: 2px 6px` + `border: 1px dashed` | 盒比文字两侧各宽 6.8px（渲染 `.pf` 是 0） | 左对齐 +1.88mm、右对齐 −1.88mm |
| `max-width: 90%` | 长文本盒宽被截到 90%，`translateX` 百分比按盒宽算 ⇒ 位移量算错 | 居中 +21.92mm、右对齐 +41.96mm |

因此 `.field-box` **不许出现** `padding` / `border` / `border-width` / `max-width` / `min-width`，
hover / selected / nodata / stale / inmulti 一律用不参与布局的 `outline` / `box-shadow` 表达。
`line-height` 也必须与渲染的 `normal` 一致，否则首行基线不同高。

（守卫：`test/canvas-align.cjs` §1–§3；实测方法见 `.workbuddy-ai/tmp/probe-align3.cjs`，
修复后最大水平偏差 41.96mm → 0.00mm。）

### I-20 PDF 与直打路径不许重编码底图

用户报「导出版本会吃底图的画质」。实测结论是**导出链路逐像素无损**——
PDF 里内嵌的就是源图原始码流。已验证覆盖：20 种底图格式（png / jpg / 16bit png /
渐进 jpg / CMYK / 灰度 / 调色板 / ICC / EXIF 旋转 / 6000×8000 / 12000×18000 …）
× 4 种纸张 × 3 种版式 = 36 组合，加 3 / 30 / 300 页三档负载，
内嵌像素一律 100%、`Filter` 保持原编码（PNG→`FlateDecode`、JPEG→`DCTDecode`
且 PDF 里能直接搜到源 JPEG 的完整字节）。

因此：PDF 与直打中的底图**只许原样内联**（`inlineUrl` 读原始字节 → base64），
不许在该链路引入图像重编码库；PDF 导出/打印的参数不许出现非 1 的 `scale` / `scaleFactor`
（会改变有效 dpi），`printBackground` 必须开。

用户显式选择 PNG 导出时，独立按指定 DPI 渲染并编码 PNG，原始素材与工程仍保持不变。PNG 文件不能回填为 PDF 的底图来源，不能将低分辨率预览图放大冒充目标分辨率输出。

「清晰度不够」的真身是**有效 dpi 不足**与**长宽比被拉伸**——
`有效 dpi = min(底图宽像素 ÷ 成品宽英寸, 底图高像素 ÷ 成品高英寸)`，
必须按较低的一轴显式告诉用户（`computeBgDpi`），避免比例拉伸时高估清晰度。

### I-21 模板固定的底图版本不可被后续编辑改写

`backgroundDesign` 必须包含工程标识和已提交版本。保存工程生成新版本，旧版本保持可读；旧编辑会话不能覆盖新版本。模板预览与打印只解析其指定版本，历史归档继续自包含素材。

### I-22 旧底图清理不得删除图层工程素材

旧单图清理只接受 `print-bg/` 下的 PNG/JPEG。转为图层工程时复制原始字节到独立的 `design-assets/`，不能共用随旧模板删除的文件。删除旧底图或旧模板后，工程仍能打开和打印。图层删除只移除引用，不能破坏撤销所需素材。

### I-23 图片与字体加载失败必须阻断出片

打印等待实际图片解码与字体加载完成，包含 CSS 背景；相同 URL 去重。加载失败或超时应报错并走已有失败留痕，不能把空白图或回退字体作为成功出片。已保存的上传字体引用缺失也必须明确报错。

### I-24 字体名规范化只有一处权威实现

`normalizeFamily`（剔除 CSS 语法字符：引号、反斜杠、分号、大括号、圆括号）只允许在 `electron/design-layout.cjs` 定义一次。
该模块零依赖，Vue 与 Node 都能 import；`fonts.cjs` 只做转出（它 require `child_process` 并在加载时读 `process.env`，渲染进程 import 会崩）。
画布、编辑器、PDF、打印、PNG 导出必须归一到同一个字符串，否则 @font-face 声明存在却匹配不上，表现为「字体没生效」——
多份拷贝一旦漂移就是静默失效。

（守卫：`test/canvas-align.cjs` §6；实测口径见 `.workbuddy-ai/tmp/probe-040.cjs`。）

### I-25 仅编辑可见的图层绝不出片

`editorOnly: true` 的图层（参考框这类「给用户对齐用」的标注）只允许出现在**编辑器画布**上。
`renderDesign(input, { includeEditorOnly })` 默认 `false`，因此打印 / PDF / 归档快照 / PNG 导出
天然排除，**默认值就是安全值**——漏传的后果是「参考框不显示」，而不是「参考框被印出去」。

- **只有 `src/components/DesignSurface.vue` 允许传 `includeEditorOnly: true`**，`electron/` 下的出片与导出路径一律不许传。
- 打印预览的图层数与最低 dpi 也只统计会印出来的图层：参考框既不该计入图层数，也不该拿它的图片拉低 dpi 报告。
- `collectFontFamilies` 的**默认口径是全量**（含 `editorOnly`），只有渲染器显式传 `includeEditorOnly: false` 才收窄。
  反了就会把编辑器里仍在用的上传字体当孤儿清掉；收窄了又会让参考框引用的字体缺失阻断整批出片。

**格式版本必须升到 3**：旧读者的 `normalizeDesign` 按固定字段表重建图层，未知字段不是被忽略而是被**剥掉**——
剥掉 `editorOnly` 后参考框就退回普通矩形，**正好会被印到身份证复印件上**。所以带 `editorOnly` 的工程标记 `schemaVersion: 3`，
旧应用明确报「不支持的底图工程版本」：宁可拒绝打开，也不静默印出参考框。版本号一律**取各特性最大值**，
不许直接赋值（原实现 `schemaVersion = 2` 会把「已是更高格式 + 恰好有分组」倒标成旧格式，等于亲手开了静默降级的口子）。

（守卫：`test/design-render.cjs` 参考框静态守卫 + 集成断言；`test/design-editor.cjs` 渲染与版本号断言。）

### I-26 打包必须显式关闭 electron-builder 的自动发布

`npm run dist` 必须带 `--publish never`，且 `release.yml` 的打包步骤**不给** electron-builder 注入任何 token。

electron-builder 的默认 publish 策略是 `onTagOrDraft`：在 tag 上构建会**自动尝试发布**到 GitHub 并索要 `GH_TOKEN`。
CI 里只有 `release-upload.cjs` 那一步有 token，打包步骤没有 ⇒ 包**明明打好了**（exe 与 blockmap 都产出），
却在末尾 `⨯ GitHub Personal Access Token is not set` 退出 1，把整步拖挂、走不到上传。
**发布是 `release-upload.cjs` 的活，两条路不能重叠。**

这个 flag 在 `accdca7` 被删过一次（v0.2.13 曾以同一原因出过空包）。之所以难发现：`ci.yml` 只跑 `npm run build` 不跑 `dist`，
所以它**只在打 tag 时才暴露**——正是「看不见的失败」。守卫（`test/e2e-harness.cjs` §6）同时钉住
「先 `npm run build` 再打包」的顺序与「打包步骤无 token」两点，避免有人换个方向把它绕回来。

### I-27 内置预设的参考框一律「仅编辑可见」，出片时不印

内置预设（`electron/design-presets.cjs`）**只保留身份证一套**（2026-10-09 收敛）。它的全部图层
（参考框 + 尺寸标注 + 说明）都必须标 `editorOnly: true`：编辑器里看得见、能选中能拖动，
打印 / PDF / PNG 导出**一个图层都不出现**。失败方式是「要印出来才看得见」的——
身份证复印件上多出一堆红虚线，而且全程不报错。

为什么把练习纸类预设删掉：练习纸不帮用户「对齐图片」，只是替他画格线（用「＋矩形」自己就能画）；
更要紧的是**内置预设越多，工程库越容易被堆满**——「常用模板」下拉每选一次就落库一份新工程，
用户为了挑顺眼的版面点几遍，就多出一堆同名工程（实测一次会话堆出 18 个）。所以内置数量必须克制，
把下拉让给「最近使用」（用户自己真正在用的工程），而不是一屏内置常量。
若日后重新加回格线类预设，务必记住两类预设的性质**相反**：格线是普通图层、**就是要印出来的**，
标成 `editorOnly` 会得到一张白纸（同样不报错）——`test/design-presets.cjs` 里保留了这条提醒。

守卫（`test/design-presets.cjs`）不只查这一条性质，还做**几何自检**——框跑出画布、同类框互不重叠且
水平居中、标注不与任何框相交，这些错误在缩略图里肉眼很难发现。另外把「内置预设恰好 1 套」也一并断言：
加预设时这里会红，提醒你确认这真的是有意的。

尺寸只收有权威来源的：身份证 / 银行卡用 ISO/IEC 7810 **ID-1 = 85.6 × 54 mm**。
户口本、驾驶证、毕业证这类各版式差异大、把握不足的**一律不内置**——内置一个「可能不对」的尺寸比不内置更糟。

（出片侧排除参考框的通用规则由 **I-25** 守。）

### I-28 打开类操作不接受路径参数

导出 PNG 之后要能「打开所在文件夹 / 用系统程序打开」。这两个动作**必须是无参的**：
路径只由主进程（`electron/printer.cjs` 的 `lastDesignPng`）在真正写出文件之后记下，
注册表那两条（`design:revealExport` / `design:openExport`）只暴露动作本身。

同一条红线的另两个实例：**打开数据目录**（`app:openDataDir`，读 `PRINTPRESS_DATA_DIR`）
与**打开素材库文件夹**（`asset:openFolder`，调 `assetLibrary.originalsDir()` 推导
`<dataDir>/design-assets`）。它们的路径同样只由主进程算，渲染层不传参。

为什么是硬要求而不是风格问题：`shell.openPath` / `shell.showItemInFolder` 会拿字符串去
**启动系统程序**。渲染进程若能指定路径，就等于拿到「以当前用户身份打开任意本地文件 /
可执行文件」的能力——一条 IPC 通道直接变成任意程序执行。这类能力不能靠调用方自觉，
必须在**通道形状**上就传不进路径：`params: {}` + `run: (_p, ctx) => ctx.printer.xxx()`。

守卫（`test/api-cli.cjs` §10）从三个层面钉住：注册表声明零参数且 `gui: 'printer'`
（CLI / agent 拿不到 `ctx.printer`，一律 `GUI_REQUIRED`）、`run` 的实现只调 printer 上那个
零参函数（正则匹配整段实现，改了参数立刻红）、`preload.cjs` 暴露给渲染层的是零参箭头函数。
另：路径只在导出**成功**后更新——渲染失败或用户取消，都不能让「打开」悄悄指向上一次的文件。
`app:openDataDir` / `asset:openFolder` 走 `gui: 'dialog'`（CLI 的 `ctx.dialog` 为 null ⇒
同样 `GUI_REQUIRED`），并断言 `asset:openFolder` 的目录来自 `originalsDir()` 而非入参。

### I-29 使用记录不得改动工程版本

「常用模板」下拉里的「常用」靠工程摘要里的 `lastUsedAt` 排序。记录一次使用走
`design:touch` → `designs.touchDesign(id)`，它**只改摘要里的一个时间戳**：

- **不碰 `revision`**：一旦顺手 `revision + 1`（或把工程内容重存一遍），用户下一次保存就会撞
  `DESIGN_CONFLICT`（「底图已更新至版本 N，当前版本 M 不能覆盖」）——而他根本没改过任何东西。
  这类故障极难排查：报错信息指向「版本冲突」，真凶却在几小时前的一次「打开」上。
- **不碰 `designs/<id>/<rev>.json`**：记录使用在物理上就改不到任何一份已提交版本的内容。

单独开一条 `design:touch` 通道、而不是顺手塞进 `design:get`：后者同时服务于出片
（`designs.resolveDesign` 走的就是它），在那条路径上写盘会让「读」带上副作用。

守卫在 `test/designs.cjs`：记录前后逐字段比对摘要（除 `lastUsedAt` 外不许有任何变化）、
工程内容逐字段不变、历史版本照旧可读，并且**记录完之后仍然能正常保存**（证明没制造出版本冲突）。

### I-30 「常用」的门槛是用户保存过，系统建的不算

「常用模板」下拉第二组的门槛是**用户自己保存过**，不是「存在过」：

- 系统按内置预设自动建出来的工程走 `saveDesign(..., { recordUse: false })`，摘要里
  `lastUsedAt` 是 `null` —— 它**不进「常用」**。
- `designs.touchDesign(id)` 对 `lastUsedAt` 为 `null` 的工程**原地不动**（返回 `touched: false`），
  所以「打开一份从没保存过的工程」也不会把它塞进常用。只有**已在常用里的**工程，打开才刷新排序。
- 老工程没有这个字段（`undefined`），按旧行为照收并按 `updatedAt` 排序——不需要数据迁移。

为什么是硬要求：每点一次「身份证（新建）」就往常用里塞一条，跟「工程库每点一次多一个」
是**同一类病**（实测一次会话堆出 18 个、装上 0.4.0 又点了 4 个）。这类问题**不在逻辑里，
在交互后果里**——逻辑断言全绿也照样发生，所以必须钉在行为上。

守卫在 `test/designs.cjs`（`{ recordUse: false }` 落库后摘要无使用记录但仍是一份 rev1 的工程、
`touchDesign` 对未保存过的工程返回 `touched: false` 且不动版本号、用户保存后才进常用）；
界面侧由 `test/design-e2e.cjs` 钉住：预设刚建出来**不出现在「常用」里**、连点两次**不新增工程**、
用户保存后才进、同名只列一条。

### I-31 素材库三原则：同内容一份原件 / 库改名不改写旧工程 / 归档不删原件

v0.5.0 M1 本地素材库在现有「内容寻址原件」（`design-assets/<sha256>.png|jpg`）之上加一层元数据
（`asset-library.json` + 缩略图 `design-thumbnails/<sha256>.png`），三层边界缺一不可：

1. **同一内容只存一份原件**。素材以 `asset_<sha256>` 为主键，重复导入=合并元数据 + 恢复归档
   （`archivedAt = null`），**绝不复制第二份字节**、绝不新建工程。这正是 I-29 那一类的病在素材侧的翻版：
   每点一次「导入」就多一份原件，会在库里堆出 N 个同图。
2. **改库名 / 标签不改写旧工程**。素材库只动 `asset-library.json` 的元数据，**不回写任何工程文件**、
   不碰 `designs.json`、不碰 `design-assets/<sha256>` 原件。库名是用户给素材起的别名，跟它当初来自
   哪份工程、哪次出片无关；改名只改条目，不改来源。
3. **归档不删原件**。归档只把 `archivedAt` 打上时间戳，`listLibrary` 默认过滤掉（`includeArchived` 才显示），
   **原件字节永远留盘**；`restore` 只是摘掉时间戳。删除素材的出口（若存在）必须走「先移 `design-thumbnails`、
   原件是否删由内容寻址引用计数决定」，绝不允许「归档即删」。

为什么是硬要求：素材库是 M1 里**唯一会落库的新增入口**，落库入口的每条行为都得钉住
「连点 N 次会留下什么」。三原则分别对应三类旧伤——除重防「堆同图」、不回写防「改名污染来源」、
不删原件防「归档即丢图」。

守卫在 `test/asset-library.cjs`：
- 原件去重：`importBytes` 同内容两次，原件数 1、条目数 1；
- 改库名不改写旧工程：改名后 `designs.json` 中同源工程 `updatedAt` / `revision` 不动；
- 归档不删原件：`archive` 后 `readAsset(id).asset.path` 仍可读、字节长度不变；
- 重复导入合并并恢复归档：先 `archive` 再 `importBytes` 同内容，条目 `archivedAt` 回到 `null`。

### I-32 清理未引用原件必须显式确认，且删除前复核仍孤儿

内容寻址池 `design-assets/<sha256>` 永不被「删图层 / 删工程 / 归档」触碰（I-31 原则③），
长期会膨胀。M1 提供一个**可选、显式**的回收入口（`asset:listOrphans` 预览、`asset:purgeOrphans` 删除），
只清「既不在任何工程、也不在素材库」的孤立原件。两条硬规矩：

1. **必须用户确认，绝不静默删**。侧栏列出孤儿数量与体积，弹「确认清理 / 取消」；`asset:purgeOrphans`
   是 `write` 通道，不在任何自动流程里触发。
2. **删除前重新算一遍引用（竞态复核）**。上传的 hash 列表里，若期间已被某工程或素材库引用
   （用户在我们列完清单后刚把它用上），一律 `kept` 跳过，**绝不删正在用的图**。
3. **路径只由 hash 拼**，不接受任意文件路径：`purgeOrphanOriginals` 只用 64 位十六进制 hash 拼
   `design-assets/<hash>.{png,jpg,json}` 与 `design-thumbnails/<hash>.png`，越界删文件无从发生。

为什么是硬要求：原件是**共享池**，一处引用就可能牵连别处。「清缓存」按钮只清 Chromium 系统缓存、
不碰 `design-assets`；但「清理未引用」是真删文件，必须比普通操作更保守——确认 + 复核双保险，
否则「想清一张废图」可能顺手删掉别人正在用的图。

守卫在 `test/asset-library.cjs`（「清理未引用原件」条）：
- 真孤儿 C 被 `purgeOrphanOriginals` 删除，原件与元数据文件消失；
- 被工程引用的 A、在素材库的 B（含归档）文件都保留；
- 竞态：列完清单后把 D 收进库，再 purge D → `removed:0, kept:1`，D 文件仍在。

### I-33 模板底图走素材库原件（assetId）；discard 按 source 分流，受管理件不即时删

v0.5.0 把「模板页上传的底图」从独占副本 `print-bg/<时间戳>.png` 并入素材库的内容寻址池
（`design-assets/<sha256>`），模板只持 `asset_<sha256>` 引用。两类底图用 `source` 元数据分流生命周期：

1. **模板底图必须引用素材库原件**。`template.background` 为 `asset_<sha256>`，**不得再写 `print-bg/` 路径副本**；
   原件生死归素材库（`asset-library`），模板层只持引用——`discardBackground` 不再 `fs.unlink` 路径，改走 `discardIfEphemeral`。
2. **`source` 是「生命周期策略」不是「来源」**，值只有两个（`design-layout.normalizeSource` 为唯一权威实现）：
   - `ephemeral`（**临时件**：模板页上传 **及底图制作页直接加图**：粘贴 / 拖入 / 「＋ 图片」对话框，
     `design:importBytes`、`design:importDialog` 通道层强制，调用方传什么都不行）且无引用 → 即时删除原件（保真旧手感）；
   - `managed`（**受管理**：素材库导入 / 已点「加入素材库」adopt / 已归档）→ **不得删除**，只撤引用（I-31 原则③）。
3. **列表只来源于 managed**：`listLibrary` 过滤 `normalizeSource(source) === 'ephemeral'`，素材库弹窗只展示受管理原件；
   临时件进了池子受引用扫描保护（不误删），但不进列表。
4. **单向升级**：`ephemeral → managed` 允许（adopt / 加入素材库即升受管理），`managed → ephemeral` 禁止。
5. **旧值兼容**：0.5.0 之前写入的 `template` / `library` 由 `normalizeSource` 读时归一为 `ephemeral` / `managed`，
   **存量磁盘数据无需迁移**；缺省一律 `managed`（漏传的后果只能是「不删」，不能是「误删」）。
6. **引用扫描接过来**：`referencedAssetIds()` 补扫模板背景 `assetId` 与全部工程文档 `doc.assets`，
   清理未引用不会误杀在用模板底图 / 工程图层图。
7. **删图层同步清理（底图制作页）**：删除图片图层后，视图把不再被任何图层引用的原件从 `doc.assets` 撤引用，
   再调 `asset:discardEphemeral(assetId, { exceptDesignId })`——`exceptDesignId` 让引用扫描**跳过正在编辑、尚未保存
   的当前工程**（磁盘是上次保存的旧版，内存态才是权威；其他工程 / 模板 / 素材库照常保护）。
   **不再弹确认框**（2026-10-11 用户明确要求：删图时弹窗会打断操作）——改为**直接删除 + 顶部提示条告知**，
   提示语写明「未加入素材库的原图已同步清理（不可恢复，此步不可撤销）」。真删了文件后，
   **只丢弃撤销 / 重做栈里「引用了这些素材」的那些快照**（「文件生死不进撤销栈」，
   防 Ctrl+Z 复活碎图），**不相关的编辑历史照留**（早先是整栈清空，代价过大：一次删图会连累无关的撤销历史）。
   撤销 / 重做栈上限 50 步（快照是整份文档、实测约 0.33 KB/图层，内存不是约束，上限只作防御性封顶）。

为什么是硬要求：模板底图与素材库原本两套池子互不相通（`print-bg` 不进素材库、不查重、丢弃即删），
既漂移又埋「静默删文件」的雷。并入后单一权威源、去重、消雷，但必须钉死「模板只持引用、
受管理件不即时删、列表只展示受管理件」三条，否则要么把别人正在用的图删了、要么把不该出现在列表的图露出来。

守卫在 `test/template-asset-library.cjs`：
- 模板上传后 `template.background` 为 `asset_<sha256>`、原件在 `design-assets/`、条目不进列表（source 过滤）；
- `discardIfEphemeral` 对 `source:'ephemeral'` 且无引用 → 删原件；对 `source:'managed'` → 保留；
- `referencedAssetIds()` 含在用模板背景 → 不列为孤儿（不误杀）；
- adopt 把原件 `source` 升 `managed`、discard 不再即时删；
- 旧值兼容：磁盘上存量 `template` / `library` 读时归一为 `ephemeral` / `managed`，分流行为不变；
- `discardBackground` 不再直接 `fs.unlink` 路径（源码文本断言）。

### I-34 模板页属性面板必须是浮层、不占列

模板工坊的右侧属性面板（`.props`）**必须是绝对定位浮层**，且只在选中字段 / 底图时渲染。

为什么：画布 `.canvas` 宽度是**固定 760px**，而 `.props` 曾经是常驻 210px 的 flex 列。实测默认窗口
1280×800（`main.cjs:103`）下 `.canvas-wrap` 只剩 **739px < 760px** → 画布右边缘被裁 21px 并出现横向
滚动条；最小窗口 960 下被裁 **341px**（只能看到 55%）。改成浮层后 `canvas-wrap` 回到 965px，画布完整可见；
960 下裁切量也从 341px 降到 115px。

这类回归**不报错、不崩溃**，只是画布悄悄少一块——正是本清单要防的「常规路径正常、边缘静默坏掉」。

硬要求：
1. `.props` 为 `position:absolute` + `right:0`，且**不得**是 flex 项（不写 `flex-shrink`）；
2. `.workbench` 为 `position:relative`（抽屉的定位参照，缺了会跑到页面右下角）；
3. 抽屉由 `v-if="selectedField || bgSelected"` 门控——常驻浮层会一直盖住画布右边缘。

守卫在 `test/ipc-hardening.cjs` §4f（前端静态核查，源码文本断言）。

### I-35 「检查更新」必须真能触发更新，失败必须可见

**「关于」对话框里的「检查更新」必须能真正开始下载并安装**，且**每一次阶段变化与失败原因都必须能被界面看到**。

为什么：2026-10-10 有 0.2.13 用户报「点更新，没有触发自动下载安装」。查下来**不是下载失败**——
「关于」里的「检查更新」只调 `version-check.cjs`（读 CDN 上 `latest.json` 的**轻量信标**）画一个红徽标，
**源码里没有任何路径通向 `electron-updater`**；真正的自动下载只发生在应用启动那一次
（`main.cjs` 的 `did-finish-load`）。于是「点按钮 → 显示『发现新版本 v0.4.0』→ 什么都不动」，
在用户眼里就是功能坏了。发版时应用已在运行的用户尤其容易踩到：他们必须先完全退出再打开才有下载。

同时暴露第二个问题：更新器当时把**所有失败只写进 `console.warn`**，而打包态没有控制台
⇒ 真下载失败也 100% 不可见，用户看到的只是「点了没反应」。这与本清单的核心命题
「看不见的失败最危险」是同一个坑。

硬要求：

1. **连线必须在**：`preload.cjs` 暴露 `startUpdate` / `installUpdate` / `onUpdateState`；
   `src/App.vue` 的「检查更新」在信标命中 `newer` 后**必须真的调 `startUpdate()`**，不能只画徽标。
2. **通道只给 GUI**：注册表里 `app:startUpdate` / `app:installUpdate` 标 `gui: 'updater'`，
   `assertCapabilities` 缺 `ctx.autoUpdate` 时给 `GUI_REQUIRED`（不能是 TypeError）；
   `normalizeCtx` 必须放行 `ctx.autoUpdate`——**漏了会被静默丢掉，通道恒 `GUI_REQUIRED`**。
3. **失败必须可见**：`auto-update.cjs` 统一经 `setState()` 把阶段与失败广播给渲染层
   （`checking` / `available` / `downloading`(percent) / `downloaded` / `none` / `error` / `unsupported`），
   **不许再只进 `console.warn`**。
4. **不支持时要说清为什么**：`startUpdate()` 拿不到更新器时返回 `{ started:false, reason }`，
   界面据此显示原因并保留「前往发布页」这条出路，而不是让用户对着没反应的按钮。
5. **不许空转重启**：`installUpdate()` 只在 `phase === 'downloaded'` 时才 `quitAndInstall`，
   否则会重启到一个什么都没变的版本。

守卫在 `test/ipc-hardening.cjs` §10（前端静态核查，源码文本断言）。

### I-36 应用内说明与 docs/使用说明.md 的章节骨架必须一致

**应用内「说明」弹窗（`src/components/GuideDialog.vue`）与 `docs/使用说明.md` 的二级标题必须逐条相同、顺序一致。**

为什么：2026-10-10 用户报「应用内使用说明还是旧的，没跟功能迭代更新」。查下来是「两处手工同步」
的必然结果——功能改了只更新了 `docs/使用说明.md`，而应用内弹窗停在 v0.2 时代，说「三步打出第一批」

### I-37 清理已删除工程的残留目录：只删不在索引里的，路径只由目录名推导

`designs.deleteDesign(id)` **只从索引移除、不删文件** —— `designs/<id>/` 与里面的版本 JSON 会留在磁盘上。
长期使用后 `designs/` 会堆满没人管的目录，而且**没有任何界面入口**能清（用户实测：索引里 1 个工程，
磁盘上 33 个目录）。所以加了 `design:purgeOrphanDirs`，界面挂在「关于 → 清理缓存与残留」按钮上，一键两用。

为什么「保留目录」是纯残留（2026-10-11 核查）：当初的理由是「未保存草稿与撤销历史」，但——
草稿活在 `localStorage`（`printpress-background-designer-draft-v1`）、撤销栈活在内存，两者都不读这些文件；
`referencedAssetIds` 也只遍历 `designs.listDesigns()`（索引）；`getDesign` / `saveDesign` 都先查索引，
查不到直接抛「底图工程不存在」。⇒ 目录在不在磁盘上，对任何功能都没有影响。

硬要求：

1. **只删不在当前索引里的目录** —— 索引里有的一律不动（那是活工程）；
2. **删每个目录前重新读一次索引复核**，防「读索引 → 删目录」之间有人刚保存了新工程；
3. **路径只由目录名推导**（`design_<24hex>` 经 `resolveInsideDataDir`），**不接受任何外部路径**（同 I-32 口径）；
4. **目录名不匹配 `design_<24hex>` 的一律跳过** —— 不认识的目录绝不碰；
5. 删不掉的（被占用 / 权限）如实报进 `skipped`，**不静默吞**。

⚠️ 与「清理缓存」并列时特别注意：缓存删了会自动重建，**残留是曾经的用户数据、删了不可恢复** ——
所以界面必须把结果逐项报出来，不能让它变成「点了个清理缓存，工程文件却悄悄没了」。

### I-38 工程包导入：先校验后发布，条目名只来自白名单，导入永远是副本

`.ppdesign` 是**用户从别处拷来的文件**——这是本项目第一次处理「不可信输入」。三条底线：

1. **条目名只认白名单**（`manifest.json` / `project.json` / `images/<64hex>.(png|jpg)` / `fonts/<64hex>.(ttf|otf|ttc|woff2?)`），
   且**先判定再落盘**：绝对路径、`..`、反斜杠变体、Windows ADS（`file:stream`）、空名、目录条目、
   超长名、大小写冲突与重复条目一律拒绝。不认识的条目**绝不落盘**。
2. **不能只信 ZIP 头声明的大小**：声明值只用于「读之前」的预算拦截，判定用**实际流出字节**；
   逐条流式落盘、边落边计数，超预算立即中断（不整体解压）。另设条目数 650、图片 64 MiB /
   工程累计 512 MiB、字体 32 MiB / 累计 128 MiB、工程 JSON 32 MiB、清单 1 MiB、总解压 768 MiB、
   压缩比与解码超时。
3. **先校验后发布，导入永远是副本**：检查阶段（`inspectPackage`）只写后端暂存区，**绝不碰工程索引**；
   提交（`commitPackage`）在同一把锁里按「准备资源 → 落恢复记录 → 发布不可变文件 → **最后**发布工程索引」
   执行，固定**新工程 ID + 版本 1**，同名不覆盖、当前画板不动。锁内复用 `designs.publishRevisionLocked`
   （不能再调公共 `saveDesign`，那会二次取同一把锁）。
4. **字体冲突走内容哈希别名**：同名不同内容生成稳定别名 `PP_Font_<sha256>`，**绝不覆盖本机已有字体**；
   缺失字体必须在提交前由用户逐条决定（替代 / 默认字体栈 / 提供字体文件），不许静默替代。
5. **重复提交幂等、失败要回滚**：令牌提交过就留档，再提交返回同一结果（不能出现两份副本）；
   中断时只回收**本次事务自己写出的**字体与版本目录，图片原件保守保留。

### I-40 混合模式 / 图片颜色调整 / 组透明度：一份实现、四处同源、滑杆走「预览→确认」

三个能力都改「像素看起来是什么样」，最容易出的错是**同一份语义在四个出片面各写一遍**，
或者**滑杆把每次 input 都记成一条撤销**。底线：

1. **清单与实现只有一处权威**：混合模式白名单是 `design-layout.cjs` 的 `BLEND_MODES`
   （**只收 CSS `mix-blend-mode` 原生支持的 16 项**，PS 专有的 linear-burn / vivid-light /
   pin-light / darker-color / lighter-color / subtract / divide 一律不收——收了就是
   「画布与 PS 不一致」的假模式）；图片调整的归一与 CSS 输出分别是 `imageAdjust` 与
   `filterOf`。前端从该模块 import 清单，**不许手抄一份**。
2. **四处同源**：编辑器画布（`DesignSurface.vue`）、PNG 导出（`design-export.cjs`）、
   打印与 PDF（`render-engine.cjs`）都必须经由 `renderDesign`，新字段才可能同时到达
   画布与成品；改渲染只能改 `renderDesign` 一处。
3. **恒等值不产生一个字符**：全默认时 `filterOf` 返回空串、`blend === 'normal'` 不输出
   `mix-blend-mode`、组透明度为 1 时输出与「没有组」逐字节一致——存量工程的渲染结果
   不受升级影响。
4. **滑杆是「预览→确认」**：调整与组透明度滑杆 `@input` 只改模型（即时预览）、
   `@change` 才 `record(draft.before)` 记**一条**撤销；拖动过程中不得调 `commit()`，
   否则拖一次滑杆能塞进上百条历史。「恢复原始颜色」走 `delete layer.adjust`（真删除），
   不是写入一组恒等值。
5. **版本 6**：使用任一新字段必须把 `schemaVersion` 抬到 6（`Math.max` 语义，只升不降），
   旧读者据此明确拒绝而不是把混合/调色丢掉后照印。

### I-41 出图格式（PNG / JPEG / WebP）：格式表单一权威源，扩展名、透明能力、DPI 元数据都由它说了算

「出图只认 PNG」曾经散落在三处（`outputPath` 的 `/\.png$/i`、保存对话框的过滤器、界面的勾选框）。
多格式化时最容易的错法是**每个格式各写一处 `if (format === 'jpeg')`**——加第四个格式时必漏一处，
而且漏的那处表现是「选完位置才失败」。底线：

1. **格式表只有一处**：`electron/export-formats.cjs` 的 `FORMATS` 是唯一权威源，
   逐格式声明 `exts` / `transparent` / `quality` / `dpi` / `label`。`design-export.cjs`
   从它导入（**不许再抄一份**），导出面板也从它导入。
2. **界面不许 import 出图实现**：`design-export.cjs` 依赖 `fs` / `path` / `crypto`，
   进不了浏览器包。格式表之所以拆成独立的纯模块，就是为了让界面读同一份而不抄第二份
   （`extensionOf` 刻意不用 `path.extname`，也是为了这个）。
3. **扩展名按 format 校验**：写盘前（`outputPath(filePath, format)`）就要拒绝
   「format 是 png 但路径写 .jpg」，不能等渲染完才发现写不进去。`.jpg` 与 `.jpeg` 等价。
4. **透明能力由格式表决定**：JPEG 没有 alpha 通道，勾了透明必须**铺画布自己的底色**
   （画布本身就是 `transparent` 时退回白色），并把这件事用 `flattened` 如实报给界面；
   界面用同一份 `transparent` 标志禁用勾选框。**静默丢掉透明层**是不可接受的。
5. **DPI 元数据如实写入、写不进就说明**：PNG 走 `pHYs`；JPEG 走 JFIF APP0 的 density
   （`units=1`），且**无论上游编码器有没有吐 APP0，结果都恰好一个 JFIF 段**；
   WebP 没有公认的 DPI 容器，**如实不写**，界面明说「文件里不会写入 DPI」。
6. **体积预估只给有损格式**：PNG 无损，体积由内容决定（矢量文字与照片能差几十倍），
   `estimateOutputBytes` 对它返回 `null`；有损格式的数字一律在界面上写「约」，
   导出完成后用**真实字节数**覆盖。

### I-43 裁切比例预设：「选 1 寸」必须是「改尺寸 + 改裁切」的同一个动作，规格不许抄第二份

这是最容易「看起来对、其实错」的一类：**改了尺寸却没改裁切，每一行代码都不报错，
打印出来却是一张被横向拉长的脸**。原因在于成品比例来自可见源区域，而不是图层毫米尺寸。

1. **比例预设只放比例，物理规格仍归 `templates.ITEM_SIZES`**：`CROP_RATIOS`（在
   `design-layout.cjs`）只允许 1:1 / 3:4 / 4:3 / 9:16 / 16:9 / A4 这类**纯比例**，
   数值量级不超过几百。证件照与卡片的毫米规格（1 寸 25×35、2 寸 35×49…）唯一权威源是
   `templates.ITEM_SIZES`，经 `app:env` 下发到界面，界面**不得再抄一份清单**。
2. **改尺寸必须连带改裁切**：静态图片的成品比例是
   `(原图宽 × crop.w) : (原图高 × crop.h)`，与图层毫米尺寸无关。所以套用尺寸预设时，
   两轴定死毫米后**必须**用同一长宽比重新裁切（`fitCropToRatio`），否则就是拉伸。
   变量图没有 `crop`（取景由 `cover` + 焦点决定），帧尺寸本身就是成品尺寸，只改尺寸。
3. **裁切数学只有一处权威实现**：`fitCropToRatio(crop, ratioW, ratioH, assetW, assetH)`
   取「放得下的最大同比例矩形」，以原裁切中心为锚点，能放下就不挪取景。
   界面只调用、不重算。
4. **浮点必须收干净**：`x + w <= 1`、`y + h <= 1` 要**严格成立**（六位小数取整 + 夹取），
   否则 `1.0000000001` 会被 `normalizeDesign` 判成「裁切区域超出原图」而拒绝整份工程。
   参数不合法时**原样返回**，宁可不动，也不要写出一份越界裁切。
5. **界面侧的两个细节**：套用后下拉立刻回位成「自定义」——不回位则同一个预设点第二次
   值没变、不触发 `change`，用户会以为功能坏了；传进 `fitCropToRatio` 的是**取整后的
   实际毫米**，不是预设的名义值，这样裁切比例与真实帧比例严格一致。
6. **预设值只按第一个冒号切分**：选项值形如 `size:photo-1` / `ratio:1:1`，而**比例 id
   本身就含冒号**（1:1 / 3:4 / 9:16…）。用「按冒号全切再解构」会把 `ratio:1:1` 读成
   id `1`，找不到预设后**静默无操作**——点了一点反应都没有，且没有任何报错。
   必须 `indexOf(':')` + `slice(sep + 1)`。守卫会用同一套规则把每个预设值解析回自己。

### I-44 图片图层的描边与投影：可选而非有默认，按 alpha 走，且不碰几何

给图片加「描边（衬边）/投影」时有三处会**静默出错**，各自都值得一条不变量：

1. **必须是「可选」而不是「有默认」**。形状的 `stroke` / `strokeWidth` 天生带默认值
   （每个形状都有一圈描边），图片一旦沿用这个约定，**所有存量工程里的每一张图都会
   凭空多出一圈线**——界面不报错、测试不报错，只有打印出来才看得见。
   所以图片的 `stroke` / `strokeWidth` / `shadow` **只在调用方真的传了才产出**；
   不传 ⇒ 与旧工程逐字节同行为，版本号也不动。
2. **投影按图层 alpha 走，不用 `box-shadow`**。图片投影落成 CSS
   `filter: drop-shadow(dx dy blur rgba(...))`，跟着图层的实际轮廓投；`box-shadow`
   按包围盒投，一张抠过底的签名图会被投出一个方盒。`drop-shadow()` 只收 `<color>`，
   不能像 SVG `feFlood` 那样把颜色与不透明度分成两个属性，所以 `shadow.opacity`
   必须在渲染侧乘进 alpha（`withAlpha`，同时支持 `#rgb` / `#rgba` / `#rrggbb` /
   `#rrggbbaa`；`transparent` 落到全透明，绝不能吐出 `NaN` 让整条 filter 失效）。
3. **描边画在框内侧、不碰几何**。描边落成一个**叠层元素** + `inset box-shadow`：
   - 不能用 `border`——会挤掉内容盒，可见源区域的比例与帧比例不再相等 ⇒ 等于把照片
     拉长（与 I-43 同一类病）。
   - **也不能用 `outline`**——实测 Chromium 把 `outline` 画在**定位子元素之下**，而图片
     正好铺满整个框，于是整圈描边被盖住、只在右/下边缘漏出约 0.2mm（300dpi 下就是 2px）。
     这个坑靠「读 HTML 字符串」是发现不了的（`outline:1mm solid #fff` 明明在 style 里），
     必须出真图读真像素才看得见。所以描边是**独立的叠层元素**，且必须排在图片**之后**。
   - 变量图的 `border-radius` 留在图层外框上，叠层要带同一个 `border-radius`（衬边才会
     跟着圆角走）；但**裁剪必须交给内层**——外框自己 `overflow:hidden` 会让投影有被自身
     裁掉的风险，而「描边 + 投影」正是证件照衬边最常见的组合。

版本号：图片的 `shadow` / `strokeWidth` 抬到 **7**（形状阴影仍是 4）。旧应用读到它
必须明确报「不支持的底图工程版本」，而不是把描边/投影静默剥掉——否则用户拿到的是一张
**缺了白边**的证件照，两边都不报错。

界面侧：图片的描边/投影参数块**只写一份**（由 `single.type === 'image'` 统管，放在
静态图与变量图两支分支之外）；关闭时把字段**删掉**而不是留一个 `strokeWidth: 0`——
后者也会把工程标成版本 7，却没给用户任何视觉差别。

守卫在 `test/design-image-effects.cjs`（可选性 + 版本 + 渲染写法 + `withAlpha` 边界 +
变量图裁剪位置 + 源码静态核查），像素级证明在 `test/design-export-e2e.cjs`
（出真图读真像素：**绿环在框内侧两侧各 1mm**、框外透明、投影投到框外、
**半透明源图 ⇒ 阴影像素也半透明**——后者正是 `box-shadow` 做不到的），
界面路径在 `test/design-e2e.cjs`。

### I-45 标尺 / 布局网格 / 吸附目标：辅助层绝不进工程文件，阈值是像素口径

1. **标尺与布局网格是视图层状态，不进工程 schema、不进 `renderDesign`。**
   这不是洁癖：它们一旦进了文档，就存在跟着出片**印到纸上**的路径（I-25 的同类事故——
   「只编辑可见」的东西漏了 `editorOnly`，参考框就被真印出去了）。放在视图层，
   从根上没有这条路径，也就不需要为它们抬工程版本号。
   行为证明（不只是静态核查）：把 `gridVisible` / `gridSpacing` / `artboard.grid` /
   `artboard.rulers` 塞进文档，`normalizeDesign` 会把它们全部剥掉，
   `artboard` 的字段清单仍是 `background` / `h` / `w` 三项。
2. **四类吸附目标各自独立开关**：画布边缘与中线 / 参考线 / 网格主格线 / 图层边缘与中心，
   界面上一类一个 toggle。缺省**网格关**、其余三类开——网格默认不显示，而「看不见的
   吸附线」比不吸附更糟（用户会以为图层拖不动了）。开关判定用 `enabled[key] !== false`
   而不是 `=== true`：调用方漏传某个键时应当**保留**该类目标，因为「少吸一条线」在界面上
   完全看不出来，只有打出来才发现歪了。
3. **吸附阈值是像素口径**（`SNAP_PX / pxPerMm`），不是毫米口径。6px 只有一份定义，
   在 `src/lib/field-edit.cjs`（模板页拖拽用的是同一个数）；界面里不许再出现一个硬编码的 `6`。
   用毫米当阈值的话，缩放一改「差 6 个像素以内就吸」的手感就漂了。
4. **网格只吸主格线，不吸次格线。** 默认间距 10mm、细分数 5 ⇒ 次格线 2mm 一根，
   而阈值换算过来约 1.7mm ⇒ 几乎每一帧都命中次格线，画布边缘与参考线再也抢不到吸附。
   次格线是「看的」，主格线才是「对的」（Photoshop 的网格吸附同理）。
5. **标尺刻度步长随缩放自适应**（画布放大用更密的步长、缩小变疏，否则缩小时数字糊成一团），
   且位置必须用**整数下标乘出来**，不能 `mm += minor` 浮点累加——第 100 根刻度会漂出
   零点几毫米，而标尺唯一的用途就是「照着它对齐」。末尾用容差判上界，
   免得 `span / minor` 恰好整除时因为 `0.9999999` 少画最后一根。
6. **标尺挂在画布外缘**（`bottom/right: 100%` + `position: absolute`），不参与画布布局，
   所以开标尺不会把画布挤小（I-34 的同类教训：任何进入布局的常驻条都会挤掉画布）。
   刻度与画布共用同一个 `pxPerMm`，缩放与滚动都不会错位。
7. **从标尺拖出参考线：拖动过程只画预览，松手才 `commit`。** 每移动一帧就 `commit` 会让
   撤销栈被几十条中间态冲爆（用户按一次撤销只回退了一帧）。落点要**夹在画布内**：
   画布外的参考线既不渲染也不参与吸附，用户从标尺往画布外一拖就得到一条看不见也吸不到的线，
   只会以为功能坏了。条数上限（100）与领域层 `LIMITS.guides` 一致，超了要明确报错。

守卫在 `test/designer-aids.cjs`（纯函数：刻度自适应与精度、网格主次格线与铺满、四类开关
各自生效、阈值口径与越界不吸、落点夹取；外加上述静态与行为核查），
界面路径在 `test/design-e2e.cjs`（真实开关标尺/网格、从标尺拖出参考线、
逐类关掉吸附目标后拖拽确实不再吸）。

### I-46 打包前的工程根目录自查：不可读条目必须拦在打包之前，清理只 rmdir 空树

`electron-builder` 会先遍历**工程根目录**再按 `files` 过滤。根目录里只要有一个
「`readdir` 列得出来、`stat` 却解析不了」的条目，它就会在 `computeFileSets` 里抛
`⨯ ENOENT: no such file or directory, lstat 'D:/个人开发/new-tools/���ﯮƤ'` 然后中断打包——
那句报错既不说清是哪个环节，也不说该删什么（2026-10-13 实际卡过一次，排查成本全花在
「这串乱码是什么」上）。这类条目**没法靠修业务代码避免**：Windows 上 Node 根本建不出来
（`mkdir` 对带非法字节的路径直接 ENOENT，实测），只可能由非 Node 的工具按原始字节建目录留下。

1. **自查必须是 `npm run dist` 的第一步**，排在 `electron-builder` 之前（事后跑没有任何意义），
   也排在 `vite build` 之前（别等构建白跑一遍才发现）。CI 的 `release.yml` 走 `npm run dist`，
   所以这一条自动覆盖 CI。守卫钉住 `dist` 里三者的先后顺序与 `--publish never`（I-26）。
2. **判据只有一条是硬的**：`readdir` 列得出来、`stat` 却解析不了 ⇒ 硬失败 `exit 1`。
   名字奇怪但能正常读写的目录只**提示**、不阻断——把正常目录误报成垃圾会让打包无故失败，
   比漏报更糟。
3. **必须以 Buffer 取名字、拼路径**。这类目录名不是合法 UTF-8，走字符串会被替换成 U+FFFD，
   连 `stat` 都对不上——这正是打包报错里那串 `���` 的来源，也是为什么不能用字符串路径去删它们。
4. **空目录提示必须递归数整棵子树**，不能只看直接子项数量：2026-10-13 那 48 个垃圾目录
   **每个里面都套着一个空的 `Microsoft`**，只看直接子项会 48 个全部漏报。
5. **清理脚本 `pack:purge` 的安全边界**：默认**只看不动**（必须显式 `--apply`）；
   **只 `rmdir`、从不删文件**（整棵树里只要有一个文件就整棵跳过，并计入 `skipped`）；
   只处理根目录的**直接子目录**。守卫钉住「脚本里不许出现 `rmSync` / `unlinkSync` / `fs.rm`」。
6. 判据、清理、退出码都在 `scripts/check-pack-root.cjs` 与 `scripts/purge-broken-root-entries.cjs`；
   守卫在 `test/pack-root.cjs`（纯函数用注入的假 io 测判据、真实临时目录测递归与安全边界、
   外加 `dist` 挂载顺序与 CI 覆盖的静态核查，共 15 项）。

### I-47 图片颜色调整滑杆：界面百分比与 schema 取值口径必须成对，换算只有一处

`imageAdjust` 里两类字段的口径不同：`brightness`/`contrast`/`saturate` 是「**1 = 原样**」的乘数（0~3），
`grayscale`/`invert` 是「**0 = 原样**、1 = 拉满」的比例（0~1）。界面上它们都是「0 ~ 上限」的百分比滑杆，
所以「上限」和「**恒等值**」这两列必须与 schema 逐字段对齐。

这里真出过一次线上问题：按字段配「除数」时把去色/反相写成 **÷1**（把 schema 里的「取值 0~1」
错当成「除以 1」），于是滑杆拖到 50 时写进 schema 的是 **50**。而 `normalizeDesign` 的 `number()`
对越界是**抛错而不是夹取**，所以画布渲染（`renderDesign`）与松手提交（`adjustChange`）都会抛，
滑杆被整体回滚并报「去色超出有效范围（0–1）」；滑杆 `step=1` 意味着 0 以外全是整数
⇒ **这两个滑杆除 0（恒等）之外没有任何档位可用**。用户看到的就是「不能自由选择调节程度」。

1. **换算只有一处**：界面百分比 → schema 一律 `÷ ADJUST_PERCENT`（=100）。不许再有
   按字段分叉的除数表，`adjustInput` 里也不许出现 `grayscale` / `invert` / `brightness` 之类的字段名。
2. **上限与恒等值都由字段表 `ADJUST_FIELDS` 驱动**：模板必须把 `max` 传进 `adjustInput`、
   把 `identity` 传进 `adjustPercent`。漏传 `max` 会让上限变成 `NaN`（滑杆彻底不能拖）。
3. **恒等值只允许两种**：比例类（去色/反相）是 **0%**，乘数类是 **100%**。去色的恒等值写成 100
   会让面板一打开就整张图变灰。
4. **守卫要钉的是「表 ↔ schema 成对」这条关系**，而不是写死数字：从 `design-layout.cjs` 解析
   `number(adj.<key>, <默认值>, <min>, <max>, …)`，逐个字段核对
   `表里上限 ÷ 100 === schema 的 max` 且 `表里恒等值 ÷ 100 === schema 的默认值`。
   以后新增调整项时口径不一致会当场变红。
5. **行为反证必须有**：断言 `grayscale: 50` 会抛「去色超出有效范围」——这就是上面那串症状的机制。
   只写静态断言的话，守卫看不见「为什么错」，改法容易走偏（本次就先误判成「被夹到上限」）。
6. 界面路径由 `test/design-e2e.cjs` 守：真实拖动去色到 50 ⇒ schema 落 `0.5`、滑杆旁回显 `50%`、
   画布上的图片真带 `grayscale(0.5)`；一次手势内连续拖动只留**一条**撤销；保存后从磁盘读回的
   `adjust` 与预期逐字段相等；「恢复原始颜色」把整块 `adjust` 删掉。

### I-48 面向用户的报错里不许出现 IPC 壳 / 绝对路径 / 内部 id / errno

起因是用户直接贴来的一条报错：

```
Error invoking remote method 'design:save': Error: 找不到底图素材 asset_973b4d1c…：
ENOENT: no such file or directory, lstat 'C:/Users/lyq/AppData/Roaming/printpress/data/design-assets/….json'.
```

这句话对用户是**零信息**：读不懂、也无法据此做任何事（甚至不知道该重装还是该重启）。
这条链路上有三个独立的失效点，任何一个单独修都不够：

- **原文本身就长这样**：主进程拼消息时把内部素材 id（64 位十六进制）与 `err.message`
  （内含绝对路径 + errno）一起拼进了句子（`designs.cjs`、`store.cjs`）；
- **整理逻辑被抄了多份、且大部分调用点没有**：`DatasetView.vue` / `TemplateView.vue`
  各写了一份剥壳正则，而 `App.vue`、`PrintCenterView.vue`、`AssetLibrarySidebar.vue` 等
  十来处直接 `error.value = err.message` ⇒ **同一条错误在有的页面干净、在有的页面是英文**；
- **未来新增调用点会重新踩坑**：只要还有人写 `error.value = err.message`，坑就还在。

所以解法是「**一份实现 + 一个收口**」，而不是逐处打补丁：

1. **实现只有一份**：`electron/user-error.cjs` 的 `toUserMessage(err, fallback)`。
   它是**零依赖纯模块**（不 require `fs` / `path` / `electron`），因为要同时被
   preload（Node）与渲染层（Vite）加载。**清洗顺序有讲究**：先砍 errno 尾巴（`ERRNO_TAIL`），
   再砍引擎散文（`ENGINE_TAIL`），再清残留绝对路径（`ABS_PATH`），最后才用
   `ASCII_PROSE` 截断——顺序反了会先吃掉 errno 前面的中文断句。
2. **收口在 `preload.cjs` 的 `invoke` 包装**：所有 `ipcRenderer.invoke` 都换成 `invoke`，
   失败时统一 `toUserMessage` 后再抛。**新增调用点自动就是干净的**，不用记得处理。
   ⚠️ 包装要求 `sandbox: false`（否则 preload 不能 require 本地模块）——守卫钉住这一点。
3. **`api.cjs` 的 `toEnvelope` 故意不动**：它是 CLI / agent 契约，原文必须保留；
   GUI 走的是 `api.call` 抛异常那条路，两条路互不影响。
4. **原文不丢，但不制造噪音**：包装把原始 err 挂在抛出错误的 `cause` 上（devtools 可查）；
   **不无条件打 `console.error`**——这个应用里不少 IPC 失败是预期内的（删掉素材后的正常查询分支
   会遇到「素材库里没有这个素材」），全部打成 error 会污染 e2e 的「界面无控制台错误」守卫，
   也会让真错误淹没在噪音里。只对「认不出来历」（落到兜底文案）的失败打日志。
5. **`err.message` 不是唯一泄漏面**：跨 IPC 传回来的**普通字段**同样会显示（`photo-match` 的
   `reason`、`photo-library` 的逐文件 `error`、`auto-update` 的 `reason`、`printer` 的
   `failureReason` 是 Chromium 的英文）。这些也要过 `toUserMessage`。
6. **清洗不许洗掉有用的话**：纯中文正文原样保留；只有「剥完一个汉字都没有」才落兜底。
   反过来，`store.cjs` 的 `读取失败` / `写入失败` 这类词有别的测试与文档钉着，
   **清洗时不能顺手删**——守卫里有反向对照断言。

守卫在 `test/user-error.cjs`（16 项）：用户报障原文的行为断言、多组真实报错的性质断言
（输出一律不含壳 / 盘符路径 / errno / 内部 id / 英文散文，且必须含汉字），
外加静态核查（实现只有一份且零依赖、`src/` 里没人再手写剥壳正则、preload 无裸 `ipcRenderer.invoke`、
九个界面真的接上了共享实现、主进程那几条原文已改掉）。

### I-49 出片分辨率：照片按图框需要的像素预降采样，原件字节一律不动

起因是 S1 压测留下的一个「产品能不能用」级别的数字：

```
500 张照片 / 原件合计 1.87 GB → 导出的 PDF 7.90 GB（374.9 s，峰值 ~1.90 GiB）
```

而 PDF 体积**与原件 JPEG 体积无关**，约等于 **嵌入照片的像素数 × Chromium Flate 重编码的
每像素字节数**。同一图框（34×50mm）实测：

| 源图 | 源 JPEG | PDF 用原件 | PDF 降采样后 | 体积比 | 像素比 |
| --- | --- | --- | --- | --- | --- |
| 3000×3000 | 3.66 MB | 16.27 MB | 0.40 MB | 40.6× | 25.8× |
| 2400×3600 | 3.51 MB | 22.60 MB | 0.39 MB | 58.2× | 35.6× |
| 4096×2731 | 4.55 MB | 13.49 MB | 0.41 MB | 32.7× | 21.4× |

外推 500 页 = 8.52 GB（与 S1 实测 7.90 GB 差 8%）。而 34×50mm 在 300dpi 下只需要
402×591px——**约 40 倍像素冗余**。

1. **一份实现**：`electron/output-dpi.cjs`。档位权威是 `export-formats.cjs` 的
   `OUTPUT_DPI_VALUES`（`[150,300,600]`，与画布导出的 DPI 档位同源，不另写一份）；
   「原图」在内部**用 `null` 表示**（不是 `0`——`0` 会被真值判断悄悄吃掉）。
   `normalizeOutputDpi` 对非法档位**报错而不静默回退**（选了 200 被当成 300 是看不见的错）。
   派生件落在数据目录 `photo-out/`，**内容寻址**命名
   （`sha256(assetId|WxH|qQUALITY|vVERSION).slice(0,40) + '.jpg'`）⇒ 同名恒同内容，
   不需要失效判断，也不会与原件混淆。
2. **只缩不放**：目标像素不小于源图时原样透传（插值放大是假细节）。PNG 保持 PNG
   （转 JPEG 会把透明压成黑，出片衬底变黑块）；JPEG 质量 88。
3. **必须分步对半降采样**：`nativeImage.resize` 一步到位的 5.1× 缩小会留下淡同心环纹，
   分步对半则与 LANCZOS 参照一致。同理**否掉 Chromium canvas**：`imageSmoothingQuality:'high'`
   在 5× 缩小时有可见同心摩尔纹，且 2.5 s/张（软件渲染）⇒ 500 张要 21 分钟；
   `nativeImage` 分步约 50 ms/张。
4. **坐标空间**（最容易安静错掉的一处）：`designs` 记录的宽高是**显示坐标**
   （`validateImage` 导入时已按 EXIF 归正），而 `nativeImage` 与 `resize` 吃**存储坐标**。
   所以 `planFor` 的入参是存储尺寸，调用方必须先过 `storageSize()`；而 cover 的缩放比
   仍要在**显示坐标**里算完再换回存储坐标。漏掉这一层不报错，只会把竖拍照片的目标尺寸
   算成 2.2 倍大（实测 1200×800 / O=6 / 34×50mm 算出 591×887 而非 603×402，纵向还是放大）。
5. **EXIF 方向必须自己写回**：`nativeImage` 忽略方向且重编码丢标记 ⇒ 竖拍照片会被 Chromium
   当横图直接画出来（转错 90°）。`withOrientation()` 写一个最小 APP1（只含 Orientation），
   顺带丢掉 GPS 等与出片无关的隐私元数据。
6. **规划与编码分开**：`planDerivatives` 只靠 `photos.geometry`（`prepareRows` 为「照片缺失
   要立刻报错」本来就要读一遍，顺手量到），**零额外 I/O**，所以预览也能准确报出
   「这次大约多大」；`prepareDerivatives` 才真读原件、缩放、落盘。预览传
   `encodeDerivatives:false`，于是**不会为一次排版确认等 25 秒首编码**。
   `stats.encoded` 区分「预计」与「实际」。
   预览只渲染当前页，张数与体积预估覆盖整个选定范围；其他页只读取尺寸元数据，
   不为估算而解码所有原件。信息不完整时隐藏体积数字，明确提示无法完整估算。
   同一照片用于多个图框时，只要任一图框需要原图，所有图框均保留原图；
   不可跳过大框需求后使用小框派生件。
7. **原件保真，只改出片表征**：派生件是新文件，原件字节一律不动。**归档快照显式按「原图」
   再准备一次**（`outputDpi: null`），不复用出片用的那份——归档要能脱离本机逐字节核对，
   留降采样件等于把「原件保真」换成「出片表征」。这同时回答了 S1 自己留的
   「明确区分原文件保真与 PDF 容器内部表示」。
8. **不静默**：界面显示本次出片分辨率与结果；留痕 detail 记下档位与降采样张数。
   **失败降级到原图**并计数上报——不静默丢照片，也不让一张坏图毁掉整批。
9. **内存纪律**：同一时刻只持有**一张**原件的字节（先规划、再逐张处理）。500 张 × 3.7 MB
   同时驻留就是 1.85 GB，正是 S1 踩过的坑。分批出片时各批的统计在 `print-batch.cjs` 汇总，
   只报最后一批会低估收益。
10. **派生件是缓存，就必须有管理入口**：内容寻址只保证「同名恒同内容」，**不保证会自己消失**。
   所以 `derivativeStats` / `clearDerivatives` 接进「关于 → 清理缓存与残留」（与系统缓存、
   工程残留同一个按钮，体积合计显示），否则它就是只涨不减的隐形占用。
   **正在出片时拒绝删**（出片中的页面正按 `pp://media/photo-out/…` 加载图片，删掉会让这一批
   全部 404，而用户看到的是「导出失败」），并把跳过原因原话报出来。
   清理逐文件计算实际释放数量与字节；文件占用或权限错误必须报告未清理项，
   其余可删除文件继续清理。不许把删除前的占用量当作已释放量。
   顺带一条排版约束：清理结果文案可能很长（「…被系统占用，将在下次启动时清理；清理了 3 个出片
   派生件（2.0 MB）」），所以 `.ar-label` 必须 `flex: 0 0 auto` + `white-space: nowrap`——
   否则中文标签会被值列挤成逐字换行的竖排。**不许靠把 `.ar-value` 改成 `flex: 1` 来「解决」**，
   那会让短值（`MIT`、`v0.6.2`）失去右对齐。两条都是实测踩出来的。

11. **保存回合必须是不动点**：`readAsset` 每次保存都按受信任原件把素材记录**重写一遍**
    （`orientation` 就是这么加进来的），所以「保存 → 主进程写回 → 再 `normalizeDesign`」
    必须逐字段相同。`design-layout` 的素材白名单漏放行一个字段，`fingerprint(已保存文档)`
    就永远比界面上的设计多一项 ⇒ 带图工程一保存仍旧显示「未保存」，且保存按钮看着像没生效
    （design-e2e「保存裁切图层」实测）。守卫在 `test/design-editor.cjs`：带 `orientation`
    的素材往返后必须逐字相同、老工程没有该字段时不得凭空补上、超出 1–8 要报错。

守卫在 `test/output-dpi.cjs`（43 项）：档位单一权威与 `null` 语义、`targetPixels` 毫米换算、

### I-50 固定图片在批量出片里的膨胀性：不带效果只嵌一份，带颜色调整/投影会逐页各栅格化一份

**状态：已量清、已修（走「乙、借 Chromium 自己烘」）。** 下面先记事实与判据，修法见文末。

I-49 的降采样只覆盖 `variable && bindColumn` 的**批量照片**图层。固定图片（底图工程合进来的大图、
固定配图、logo）走的是另一条路：渲染成 CSS `background-image`、在 HTML 里**只内联一份**。
这条路的成本**不随页数增长**，所以不进降采样范围是正确的——但这个「正确」依赖一个可测前提。

前提与反例（实测，`test/fixed-image-dedupe-e2e.cjs`，3000×3000 固定底图，34×50mm，21 页）：

| 固定图片这一层 | 单页 | 21 页 | 相对单页 | PDF 里图片对象 |
| --- | --- | --- | --- | --- |
| 朴素（无属性） | 6.67 MB | 6.69 MB | **1.00×** | 1 → 1 |
| 仅 `opacity: 0.85` | 6.67 MB | 6.69 MB | **1.00×** | 1 → 1 |
| 仅颜色调整 `adjust` | 0.63 MB | 13.14 MB | **20.77×** | 2 → 42 |
| 仅投影 `shadow` | 0.67 MB | 13.83 MB | **20.78×** | 2 → 42 |

1. **只做绘制就复用**：朴素与仅 `opacity` 时 Chromium 复用同一份图片 XObject，
   页数再多也只嵌一份（500 页的整份 PDF 仍是 6.7 MB）。
   加 alpha 属于绘制时套参数，**不算新图片**，所以安全。
2. **一旦要「算出新像素」就每页各栅格化一份**：CSS `filter`（颜色调整）与
   `filter:drop-shadow()`（投影）都会让 Chromium 把合成结果栅格化成一张新位图，
   而这张位图**每页各来一份**，成本按「印刷面积 × 页数」线性增长。
3. **每页那份的尺寸由「印出来的面积」决定，与原件大小无关**：栅格化约在 384 dpi 上下
   （34×50mm ⇒ 0.63 MB/页；A4 满版 ⇒ 19.67 MB/页）。
   于是**A4 满版带滤镜底图 500 页约 9.8 GB**——与 S1 实测的 7.90 GB 同一量级，
   是一条与照片路径**完全独立**的膨胀机制。
   A4 三页正好 3.00×，线性关系确认。
4. **换效果机制没用**（已实测，省掉一条错路）：把颜色调整改成 SVG `feComponentTransfer`、
   把投影改成 SVG `feDropShadow`（含形状那套 `<image filter="url(#ds)">` 写法），
   全都是 20.98×，与 CSS 侧逐字节同量级。**Skia 的 PDF 后端表达不了滤镜，只能栅格化**，
   换写法不改变这一点。
5. **触发路径在界面上可达**：底图编辑器图层属性面板有亮度/对比度/饱和度滑杆（`adjust`），
   说明里也明确写了图片的「描边（衬边）与投影」。所以「给底图里的 logo 加个投影、
   再当模板底图批量出片」就能踩到。
6. **判据（修好之后）**：`test/fixed-image-dedupe-e2e.cjs` 第 3 节钉的是**修好后的行为**
   （带 `adjust` / `shadow` 也必须复用、比值 < 1.2、图片对象 ≤ 2）。它同时也是
   「修法真的生效了」的唯一证据——**不要删掉那一节**。
   比值之外还钉了**边际成本**（21 → 42 页每多一页只许涨几十字节），因为比值会被常量开销
   干扰：单页 0.5 MB 里图片占九成，多嵌一份常量就正好 2×，看不出「是不是真的与页数无关」。

修法（**已实现：乙**）：

- **乙（采用）、借 Chromium 自己烘**：出片前把这一层（连旋转/裁切/翻转/调整/投影/描边一起）
  单独渲染成一张 PNG，再用它顶替该图层。效果由 Chromium 计算，一致性由像素与几何测试验证，
  不必复算滤镜。落点：
  - `electron/output-dpi.cjs`：`bakeTargets`（判据复用渲染侧的 `filterOf`，不另写一套）/
    `bakeGeometry`（外接框复用 `shadowRegion`）/ `bakeName`（内容寻址）/
    `planFixedBakes`（零 I/O）/ `prepareFixedBakes`（异步烘 + 落盘）/ `readFixedBakes`（同步读命中）。
  - `electron/design-layout.cjs`：`renderDesign` 的 `options.bakedLayer(layer)` 渲染期覆盖，
    把该层画成全素轴对齐图片。**这是渲染期覆盖，不动存盘 schema**（与变量图的 `photoUrl` 同一个模式）。
  - `electron/print.cjs` 的 `warmBatchBakes` + `electron/api.cjs` 在出片动作前 `await`。
  - **缓存键包含图层宽高、旋转角度与裁切后的外接框**。只记录外接框会让 +30° 与 -30°
    共用错误缓存。2026-10-16 将缓存版本升为 2；旧缓存不再命中，仍可通过清理缓存回收。
  - **异步边界放在出片动作上**：`renderImage` 要拉离屏窗口截图（异步），而 `buildBatchHtml`
    是同步的、被预览/CLI/二十来个测试同步调用，不能改签名。所以「出片前预烘 + 渲染期只读命中」，
    与 I-49 的 `planDerivatives`/`prepareDerivatives` 同一个套路。**没命中就不烘**（该层照旧按原样渲染）。
  - **`opacity` 与 `blend` 不烘进像素**（实测两者不破坏复用），留在替换元素上——留在外层才能让
    「组透明度 × 图层透明度」只生效一次（烘进去再乘一遍会变暗）。`bakeName` 的键里也**不含**这两者，
    所以「只调了透明度」不会触发重烘。
  - **烘焙画布裁到画布之内**（`bakeGeometry(layer, artboard)`）：渲染根 `.print-design-root`
    带 `overflow:hidden`，越出画布的部分本来就看不见。不裁的代价实测过——34×50mm 画布上
    满版底图 + 投影（外接框 51.5×67.5mm）时 Chromium 会**按页边界把这张图切成两片**
    （608×688 + 608×110），两片都嵌进 PDF：单页 0.501 MB / 2 个图片对象 → 21 页 1.009 MB / 6 个。
    多出来的是**常量**（42 页也只 1.021 MB），不是膨胀；但它让比值停在 2.01×、还烘了三分之一
    印不出来的像素。裁掉即回到 1.03×。**只有纵向溢出会触发切分**（横向溢出 1.25mm 实测仍是 2 个对象）。
- **甲（未采用）、自己复算烘焙**：把 `adjust` / `shadow` 应用到源图再降采样。
  `adjust` 是 CSS filter 规范里逐通道的确定公式，可以精确复算；但 **`shadow` 需要一层模糊**，
  要与 CSS `drop-shadow()` 的观感对齐（Skia 用三重盒式模糊逼近高斯），复算有保真风险、
  得做像素级对照。既然乙能「按构造成立」地拿到同一个结果，甲只多出一份需要长期维护的滤镜复算，
  不划算。**记在这里是为了省掉后来者重新试这一遍。**

守卫在 `test/fixed-image-dedupe-e2e.cjs`（`npm run test:fixed-image-dedupe-e2e`）：朴素/仅透明度/
仅混合必须去重（比值 < 2、图片对象 ≤ 2）、HTML 里只内联一份、带 `adjust`/`shadow` 烘焙后也必须
去重且不残留 CSS 效果、烘焙件的像素真的带上了效果（亮度比 ≈1.2、投影落在图层框外且偏右下）、
烘焙画布裁到画布之内、**边际成本**（21 → 42 页）、A4 每多一页 < 1 MB、
以及**方法灵敏度对照**（21 张真不相同的图必须涨到 21 个图片对象、比同一张大大 3 倍以上——
否则说明度量分不出「复用/不复用」，前面的结论不能采信）。

**已量清、尚未做的下一条边界（别当成没发现）**：烘焙件固定用 **PNG**（因为投影层必须要 alpha），
而 PNG+Flate 对照片类内容是 **2.6 字节/像素**（A4 满版 @300dpi = 2480×3508 ⇒ 单份 22.62 MB，
实测）。对比之下，修法前 Chromium 自己逐页栅格化的那一份是 19.67 MB/页——所以**单页作业反而略大**
（22.62 vs 19.68），只有页数一多才赚。若该层**无投影且未旋转**，烘焙画布必然被图片铺满（不透明），
改存 JPEG 可再省约 3.5×（≈6.4 MB）。**没顺手做**的理由是它有正确性前提：一旦旋转或带投影，
外接框的角上是透明的，JPEG 会把它们画成黑角——那是肉眼可见的坏图。要做得连
「无投影 && rotation===0 && 素材是 JPEG」这个判据一起量、一起守（与 I-49 派生件
「跟着源容器走」同一条纪律），不当作附带改动塞进来。
另外体积模型 `PDF_BYTES_PER_PIXEL = 1.6` 是按「1.2~2.6 字节/像素」取的中值，所以照片类烘焙件的
**预估会偏低约 1.6×**——在模型自己声明的容差内，且导出后一律用真实字节覆盖，不算缺陷。

### I-51 素材保存仓库与临时底图分池存放：managed 只落 `design-assets/`，ephemeral 只落 `ephemeral-assets/`

原件照旧按内容寻址（`<sha256>.<ext>` + 同名 `.json` 边车，一处一份），但**两个池子物理分开**：

1. **受管理件只落 `design-assets/`**（`POOL_MANAGED`）：素材库导入、`asset:adopt`、
   工程包导入、旧 `print-bg` 迁移后升 managed 的场景。侧栏「打开素材库文件夹」开的
   就是这个池——用户在那里看到的必须全是素材库原件。
2. **临时底图只落 `ephemeral-assets/`**（`POOL_EPHEMERAL`）：模板页上传、底图制作页
   粘贴 / 拖入 / 「＋ 图片」对话框、配图照片（`designs.importBuffer` 按 `poolOfSource`
   分流）。它们受引用扫描保护（不误删），但不进素材库列表（I-33 原则③）。
3. **升级连字节一起搬**：`ephemeral → managed` 的唯一出口（adopt / 加入素材库）必须把
   图片与边车一起迁进 `design-assets/` 并改写边车 `path`（`setAssetSource`）；只改标记会让
   「打开素材库文件夹」看得见临时件、备份 / 清理也没法只针对素材库。降级
   （managed → ephemeral）仍然禁止。搬迁顺序：复制图片 → 写新边车 → 删旧边车 → 删旧图，
   中途被杀最多留一份重复（`locateAsset` 取 managed 那份），绝不把图搬丢。
4. **同内容两池不重复**：导入先按 hash 双池定位（`locateAsset`），已在任一池子即返回既有
   记录（I-31 原则①）——绝不因为这次传了别的 source 就存第二份字节。
5. **旧数据启动时迁移**：`designs.migrateEphemeralOriginals()` 把存量 `design-assets/` 里的
   临时件迁到 `ephemeral-assets/`（幂等、单件失败不阻断启动）。工程文档里的旧路径是合法
   历史值：`readAsset` 的 `claimedPath` 容忍「同 hash、另一池、同扩展名」的声明（指向别的
   hash / 池外路径一律仍是损坏），打开 / 保存时 `canonicalAssets` 改写成真身。
6. **不同步前端的旧路径必须照样显示**：界面手里的工程文档 / 未保存草稿可能还指着搬迁前的
   池路径（编辑器画布按 `doc.assets[].path` 拼 `pp://media` URL，前端不参与搬迁同步）。
   `media-protocol.cjs` 因此对 `<pool>/<sha256>.<ext>` 也按 hash 解析真身（边车缺失才退回
   直读）；保存时主进程的规范化文档会把渲染侧文档同步成真身（保存回合依旧是不动点，I-49 第 11 条）。
7. **读取、清理、保护全部双池**：`readAsset` / `assetInfo` / `assetGeometry` / `assetSource` /
   `assetBytes` 双池定位；`findOrphanOriginals` / `purgeOrphanOriginals` / `discardIfEphemeral`
   两个池子都扫都删；`design-export.outputPath` 的受保护目录含两个池。

为什么是硬要求：素材保存仓库与临时底图混在一个池子里，「打开素材库文件夹」看得见临时件，
备份 / 清理也没法只针对素材库；更早的 `print-bg` 独占副本与素材库两套池子互不相通，既漂移又埋
「静默删文件」的雷（I-33 的来路）。分池之后：素材库 = `design-assets/`、临时底图 = `ephemeral-assets/`，
一眼可分、各自可独立备份，原件生死仍只归内容寻址与 `source` 分流管。

守卫在 `test/asset-library.cjs`（I-51 条）：
- 受管理件落 `design-assets/`、临时件落 `ephemeral-assets/`，互不串池；同内容跨池去重不产生第二份字节；
- adopt 后原件（含边车）搬进 `design-assets/`、临时池不留件，旧工程文档路径被改写；
- `migrateEphemeralOriginals` 幂等；旧版 `design-assets/<hash>` 路径的工程照常打开并改写成真身；
  指向别的 hash 的声明仍被拒；
- 临时池里的孤儿列得出来、删得掉。

### I-52 对外口径里的数字必须与实现一致：当前口径文档严格核对，历史快照按行内日期/白名单豁免

**现象**：README、使用说明里宣传的操作数与测试套件数这类数字是可验证的承诺，但它们此前没有守卫。

- `docs/v0.7功能建议-参照Compositor.md` 里曾写着「`api-cli` 有 90 个操作」，实测 96——漂了三个版本（2026-10-18 修正），
  直到一次外部审查才发现（对比 README 里那 4 处 96 一直是对的，说明只靠人盯着必然漏）；
- 每加一个测试套件，README 的套件数就过期一次；而它又恰好是外部判断项目活跃度最省事的依据；
- 反方向同样有风险：把承诺文档（契约、使用说明）悄悄归进私人资产，外部读者就拿不到承诺本身。

**规则**：

1. 实测值只有三个权威源：`electron/api.cjs` 的 OPS 注册表（操作数）、`package.json` 的
   `scripts.test`（套件数）、`docs/不变量契约.md` 的 `### I-NN`（不变量条数）。
2. **当前口径文档**（`README.md`、`docs/使用说明.md`、`docs/底图制作使用说明.md`）里的每一个
   数字型宣称都必须等于实测值；README 还必须**声明**这些数字——不许为了不红而把卖点删掉。
3. **历史快照**写的是「当时是什么样」，两种情形豁免：行内自带日期（`（2026-10-01；12 套件…）`
   这类进度快照），或整篇登记进 `HISTORY_DOCS` 白名单。白名单必须在仓库里真实存在、且确实含
   数字型宣称——不许腐烂，也不许拿来悄无声息地吞掉新文件。
4. 被 `.gitignore` 归为私人资产的本地笔记不参与对外口径核对；反过来，`README.md`、
   `docs/不变量契约.md`、`docs/使用说明.md` **必须不被忽略**。
5. 套件数口径与 `test/api-cli.cjs` 里那条动态守卫保持一致（都按 `split('&&')` 后匹配
   `node test/`），操作数口径与它的 `api.describe().length` 同源——两个口径不一致会让
   README 怎么改都红，守卫就成了摆设。

**为什么是硬要求**：数字型卖点漂移是「没人会报错的错误」——界面一切正常，只有读到文档的人被
误导；它又便宜到任何人都能顺手核对。把口径变成断言，才不必依赖「谁记得改」。

守卫在 `test/claims.cjs`（I-52 条）：
- 三条实测源都能解析（注册表命名空间必须是已知的 11 个、操作名不重复、`ipc-wiring` 动态枚举）；
- README 与两份使用说明逐条核对，写错即红并打印行号与原文；
- 白名单之外的文档出现陈旧数字即红（含「新文件也不能漏网」）；
- 白名单每条必须存在且确实含宣称；`.gitignore` 的私人资产分类与「承诺文档不得被忽略」两个方向都钉住。

### I-53 导入闸门：坏文件挡在解析入口，原型槽表头不许吞掉整列数据

**现象**：`xlsx@0.18.5` 有两条官方已无修复版本的安全公告（原型污染 + ReDoS），而
`electron/importer/excel.cjs` 的 `XLSX.readFile` 正是**用户随手拖进来的文件**的解析入口；
另有一条与安全公告无关、但同样静默的坑：表头只要叫 `__proto__`，`rec['__proto__'] = '张三'`
就会被原型 setter 吞掉——这一列在界面上列得出来、填充率却永远 0，出片时印成 `[object Object]`。

**规则**：

1. **体积与规模上限**（`LIMITS`，取「正常名单不可能达到」的量级）：单文件 64 MB、工作表 64 张、
   单表 20 万行、1024 列、合计 200 万格、单格 3 万字符。超限一律**拒绝并说明怎么自救**
   （「先在表格软件里拆分」），不做静默截断——截断会让用户拿到少了一半的名单。
   `sheetRows` 让解析器在超行时提前收手，不把整张巨表读进内存。
2. **原型污染守卫**：解析前后对 `Object.prototype` 的自有属性名做快照，多出来的就是这次解析注入的。
   只检出不够——注入的属性会留在进程里影响之后所有代码，所以**先按快照删除再报错**。
3. **原型槽表头**：`keys.cjs` 的 `normalizeHeaderKey` 对 `__proto__` / `constructor` / `prototype`
   加 `col_` 前缀（alias 仍是用户原表头，界面显示不变）；`dataset.cjs` 建行对象时对这类键走
   `Object.defineProperty` 而不是直接赋值——两道，因为直接赋值的失败方式是**静默**的。
4. 闸门文案同样受 I-48 约束：纯中文、无绝对路径、无 errno、不夹内部细节。

**为什么是硬要求**：换解析器是产品决策（`xlsx` 已无维护版本可升），在决策落地之前，至少要让
「明显不该导入的文件」和「会静默改坏数据的表头」在入口就停下；而静默失败最贵——没有报错，
只有一张印错的证书。

守卫在 `test/sheets-import.cjs`（I-53 条，上限可注入所以测试不必真造 64 MB 文件）与
`test/m1-import.cjs`（键名规范化）：
- 超限文件被拒、正常文件不被误拒（回归）；
- 行 / 列 / 超长格三条判据各一发，超长格文案带行号；
- 注入 `Object.prototype` 后被检出**且现场已清理**；
- 闸门文案无绝对路径 / 无 errno / 不夹内部细节；
- `__proto__` 表头的整列数据能读回来，且没有污染进程级原型。

### I-54 界面与命令行共用数据目录时，写入必须互斥而不是互相覆盖

**现象**：界面与 `bin/pp.cjs` 默认指向同一份数据目录，两边都走 `store.cjs` 的
「读整份 JSON → 改 → 整份写回」。原子替换（临时文件 + rename）只保证单文件不半截，
**不保证语义正确**：两个进程各自读到旧值、各自写回，后写的那次会安静地吃掉前一次的修改
——命令行刚导入的名单，被界面的一次编辑整体覆盖，谁都不会报错。

**规则**：

1. **GUI 生命周期持锁**：`electron/data-lock.cjs` 在 `data/` 下落 `data-dir.lock.json`
   （`wx` 独占创建，内容是 `{pid, role, startedAt, beatAt}`），取锁排在种子与各类迁移**之前**
   ——那些步骤本身就会写 JSON。心跳 10s、租约 45s，被强杀后最坏 45s 恢复可写。
2. **陈旧锁必须自愈**，否则一次崩溃就让数据目录永久不可写：pid 已不存在（`EPERM` 视为存活）、
   心跳过期、心跳早于本次开机（Windows 会复用 pid）、锁位是普通文件或坏 JSON，四种都按可回收处理。
3. **只有写操作探测**：`api.call` 里在**写权限闸门之后**探一次（顺序不能反——缺写权限必须报
   `WRITE_FORBIDDEN`，否则 I-18 那条遍历全部写操作的守卫会先红）。只读命令（list / render /
   validate / inspect）永远不受限，否则窗口开着时 agent 连数据都看不了。
   错误码 `DATA_DIR_BUSY`，`pp` 退出码 4，文案说清出口（「先关掉批印坊窗口」）。
4. **锁的边界条件**：锁路径**每次现取** `process.env.PRINTPRESS_DATA_DIR`（照抄 `store.cjs`
   的加载期缓存就会指错目录）；`copyDirSync` 迁移数据目录时**不搬锁文件**（搬过去就是一把别人
   pid 的死锁）；释放失败只告警不抛（否则会顶掉调用方真正要报的结果）；GUI 与 GUI 之间交给
   Electron 的 `requestSingleInstanceLock()`，文件锁只管 GUI vs 命令行这一半。

**为什么不是更彻底的方案**：在 `saveJson` 里加一把短锁只把窗口从「整个读写期间」缩到「写期间」，
交错依然丢更新，却给人「已经修好了」的错觉；给六个领域模块的 JSON 都加版本号做 CAS 语义最准，
但要改掉全部损坏恢复路径与大量裸写夹具（`designs.cjs` 的 `DESIGN_CONFLICT` 已是范式），
留给 v0.7 单独做。这里只做**可见的互斥**：宁可让用户看到「窗口开着时命令行只读」，也不要悄悄丢数据。

守卫在 `test/data-dir-lock.cjs`（19 项）：真起一个存活进程验「活跃持有者被拒且不删别人的锁」、
四种陈旧锁自愈、锁路径随 env 现取、释放失败不抛、只删自己的锁、BUSY 文案合规（I-48）、
`main.cjs` 取锁顺序与 `process.on('exit')` 兜底、写闸门接在权限之后、迁移不搬锁、`pp` 退出码。

### I-55 照片任务历史溢出改归档，不静默销毁

**现象**：`photo-library.cjs` 的任务摘要列表写盘时 `.slice(0, 100)`——第 101 次导入之后，
最早的记录就再也找不到了。照片导入恰好是最容易出问题的一步（同名学生、目录被改名、图缺张），
事后回溯「那次绑的是哪个目录、匹配了多少张」只能靠这条记录，而它已经被静默删掉了。

**规则**：超出 100 条的记录写入 `photo-import-tasks-archive.json`——只追加、按 `taskId` 去重、
自身保留最近 500 条防止无上限增长；界面列表口径不变（仍只留最近 100 条，`listTasks` 返回 30 条）。
归档目前没有界面入口：它的价值是「记录还在」，不是「列表更长」——**不新增操作**，
免得为了一个内部归档去动对外操作数口径。

守卫在 `test/photos.cjs`：满 100 条后写入一条，被挤出的那条必须出现在归档里且形状与列表一致；
重复写同一 `taskId` 不重复归档；归档自身有上限。
