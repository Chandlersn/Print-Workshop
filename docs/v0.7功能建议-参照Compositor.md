## 二、P0：低投入高收益

### 1. 图片图层颜色调整

Compositor 有 13 种调整图层。PrintPress 的渲染走 HTML/CSS，**图片调整用 CSS `filter` 即可落地**：
`brightness/contrast/saturate/grayscale/invert`（可选 `sepia`、`hue-rotate`）。
建议先在变量图和普通图片图层的属性面板给 5 个滑杆，字段进图层 schema（加性，默认恒等），
渲染层把 `filter` 加进 `<img>` 样式行。

- 场景：扫描签名翻拍后不黑不淡、logo 单色化、旧照片补救、印刷前统一色调。
- 打印保真：CSS filter 在 print 管线的 `printToPDF` 下同样生效（Chromium 打印支持 filter），
  但需按既有规矩补一条 e2e 截图断言。

### 2. 混合模式（先上 Canvas 2D 原生 15 种，其余标记为逐像素补）

Compositor 支持 27 种（v3 起进格式），且**没有走任何绘图框架**——WebKit/AppKit 的
filter 不支持，于是 `LayerBlending.swift` 对 26 种各手写一版 Porter-Duff 源码实现。
PrintPress 的对应现实：

- **Canvas 2D `mix-blend-mode` 原生即支持约 15 种**（normal + multiply / screen /
  overlay / darken / lighten / color-dodge / color-burn / hard-light / soft-light /
  difference / exclusion / hue / saturation / color / luminosity）。先上这 15 种，
  覆盖绝大多数底图叠印/水印场景，CSS 一行落地。
- 剩下的（linear-burn / linear-light / vivid-light / pin-light / darker-color /
  lighter-color / subtract / divide…）**没有 CSS 对应**，要逐像素补才有；
  且各家公式与 PS 标准存在色差（该仓库实测软光/色相系最多差 25 色阶，与 PS 23.5 行为一致）。
  打印场景对色准敏感 ⇒ 上任何混合模式前，先补「canvas 预览 vs print 管线」双通道截图断言。
- 场景：艺术底图叠印纹理、水印压图、模拟烫金/反白。字段加性、默认 `normal`。
- **组透明度**顺带补上（P0 低成本项）：schema 里组目前无 opacity，加一个可选字段，
  语义与 Compositor 一致——**组透明度相乘到所有成员，组的混合模式固定 normal**。
  CSS 用嵌套容器 `opacity` 天然表达，零像素成本。

### 3. 滤镜式 UX：「预览→确认」，单步撤销

Compositor 的滤镜流程是「面板内实时预览 + OK/Cancel，整次调整只算一步撤销」
（`FilterHost.swift`，三阶段 arm→live→commit）。PrintPress 属性面板当前是即时写图层，
滑杆拖一次进一次撤销栈——颜色控件踩过的坑（I 系列里有双绑告诫）会在调整类控件上重演。
建议：调整类控件出「预览→确认」两步，commit 时才 `pushHistory`。这与 v0.6 计划里
「结果集中、不弹窗遮挡」的页面内交互也不冲突。

## 三、P1：打印场景直接受益

### 4. 标尺 + 布局网格 + 吸附目标细化

已有 guides + `snapDelta`，缺三样：

- **标尺**（可开关）+ 从标尺拖出参考线（当前只能输入位置数值）；
- **布局网格**：可调间距与细分数（卡片排版对齐神器）；
- **吸附目标分别开关**：画布边缘 / 参考线 / 网格 / 图层边缘与中心，各一个 toggle。

打印卡片（身份证、证书、席卡）是「毫米级对齐」生意，这三样是把「凭手感摆」变成
「摆得准」的关键。成本中等，全在前端。

### 5. 带比例的裁切预设 —— ✅ 已实现（2026-10-13）

Compositor 的 `CropTool.swift` 内置常见比例（3:4、9:16 等）并支持 Option 对称裁切。
PrintPress 变量图已有 `crop` + `focal`，但比例要手算。建议：

- 图片/变量图裁切面板给比例预设：1 寸(25×35mm)、2 寸(35×49mm)、3:4、9:16、A4 比例、
  自由；按打印物理尺寸（mm）表达，而不是像素比。
- 与 v0.6 S5「单人裁切覆盖设置」合做：那是「只调整这一位人员」的单独裁切，
  预设比例直接复用同一控件。

> **落地结果**：图片与变量图的属性面板都多了一个「成品尺寸 / 比例」下拉
> （`data-testid="design-size-preset"`），首项是「自定义（不改动）」= 文档里的「自由」。
> 下拉分两组：**证件照与卡片（毫米）** 由主进程经 `app:env` 下发（就是多联拼版用的
> `templates.ITEM_SIZES`，不抄第二份），**仅比例** 用 `design-layout.cjs` 的 `CROP_RATIOS`
> （1:1 / 3:4 / 4:3 / 9:16 / 16:9 / A4，只放纯比例）。
>
> 与建议的**一处有意偏离**：没有把 mm 规格也塞进 `CROP_RATIOS`。规格归
> `templates.ITEM_SIZES`、比例归 `CROP_RATIOS`，这样「1 寸是多少毫米」永远只有一个答案。
>
> 实现上最关键的一条：**「选 1 寸」必须是「改尺寸 + 改裁切」的同一个动作**。
> 成品比例来自可见源区域 `(原图宽 × crop.w) : (原图高 × crop.h)`，与图层毫米尺寸无关——
> 只改尺寸不动 `crop`，用户选完 1 寸得到的是一张**被横向拉长的脸**，而每一行代码都没报错。
> 所以套用预设时两轴定死毫米后，静态图片立刻用同一长宽比重算裁切（`fitCropToRatio`，
> 取「放得下的最大同比例矩形」，以原裁切中心为锚点，六位小数取整并夹取，
> 保证 `x + w <= 1` 严格成立——浮点尾巴 `1.0000000001` 会让 `normalizeDesign` 拒绝整份工程）。
> 变量图没有 `crop`（取景由 `cover` + 焦点决定），帧尺寸本身就是成品尺寸，只改尺寸。
>
> 两个界面细节：套用后下拉立刻回位成「自定义」（不回位则同一个预设点第二次值没变、
> 不触发 `change`，用户会以为功能坏了）；传进 `fitCropToRatio` 的是**取整后的实际毫米**，
> 不是预设的名义值，这样裁切比例与真实帧比例严格一致。
>
> 守卫：`test/design-crop-presets.cjs`（13 项，纯函数数学 + `normalizeDesign` 集成 +
> 源码静态核查，契约 I-43）；界面路径在 `test/design-e2e.cjs`（下拉选项、25×35 落盘、
> 可见源区域比例 == 25:35、裁切不越界、下拉回位、比例预设只改高度、撤销连带回退裁切）。

### 6. 图片图层的描边与投影 —— ✅ 已实现（2026-10-13）

Compositor 的图层样式有 6 种（stroke / shadow / colorOverlay / innerShadow / outerGlow /
innerGlow），**形状已进 schema**（`shadow`/`stroke`），但**图片图层没有**。
PrintPress 先上两种即可覆盖高频场景：描边（证件照白边/衬边）与投影（照片卡立体感）。
从它的实现里值得抄的细节：

- **按图层的 alpha 走，不按包围盒**：图片用 CSS `filter: drop-shadow()`（follows PNG alpha）；
  形状可继续现有 SVG filter（`feFlood` 已在用）。别图省事用 `box-shadow`，矩形图一投一个方盒。

> **落地结果**：静态图片与变量照片的属性面板都多了「描边（衬边）」与「投影」两组控件
> （`data-testid="design-layer-stroke"` / `design-layer-shadow`）。投影沿用与形状**同一个**
> `shadow` 结构（dx/dy/blur/color/opacity），只是渲染方式不同：形状走 SVG
> `feGaussianBlur`+`feFlood`，图片走 CSS `filter: drop-shadow()`。`drop-shadow()` 只收
> `<color>` 而不能像 `feFlood` 那样把颜色与不透明度分成两个属性，所以新增 `withAlpha()`
> 把 `shadow.opacity` 乘进 alpha（同时支持 `#rgb` / `#rgba` / `#rrggbb` / `#rrggbbaa`，
> `transparent` 落到全透明、绝不吐 `NaN`）。
>
> **与建议的一处有意偏离**：这两个字段是「**可选**」而不是「有默认」。形状的
> `stroke`/`strokeWidth` 天生带默认值（每个形状都有一圈描边），图片一旦沿用，**所有存量
> 工程里的每一张图都会凭空多出一圈线**——用户没要求过，界面不报错、测试不报错，只有打印
> 出来才看得见。所以只在调用方真的传了才产出字段；不传 ⇒ 与旧工程逐字节同行为。
> 只给 `stroke` 不给宽度时宽度取 0（不猜用户想要多宽）；缺省色是白（衬边的高频用法）。
>
> **描边为什么不是 `outline`（踩过的坑）**：第一版按直觉写成
> `outline:Nmm solid color` + `outline-offset:-Nmm`，文本断言全绿——`outline:1mm solid
> #fff` 明明在 style 里。**出真图读真像素才发现：Chromium 把 `outline` 画在定位子元素
> 之下**，而图片正好铺满整个框，于是整圈描边被盖住、只在右/下边缘漏出约 0.2mm
> （300dpi 下就是 2px）。改成「**独立叠层元素** + `inset box-shadow`」并让叠层排在图片
> **之后**，两侧才各出现完整 1mm 的环。这条写进了 I-44 与守卫。
> 也没用 `border`：`box-sizing:border-box` 下 border 会挤掉内容盒，可见源区域的比例与
> 帧比例不再相等 ⇒ 等于把照片拉长（与 I-43 同一类病）。
>
> 变量图的 `border-radius` 留在图层外框上（叠层带同一个圆角，衬边跟着圆角走），但
> **裁剪挪到了内层**——外框自己 `overflow:hidden` 会让投影有被自身裁掉的风险，而
> 「描边 + 投影」正是证件照衬边最常见的组合。
>
> 版本号抬到 **7**（形状阴影仍是 4）：旧应用读到它必须明确报「不支持的底图工程版本」，
> 而不是把描边/投影静默剥掉——否则用户拿到的是一张**缺了白边**的证件照，两边都不报错。
>
> 守卫：`test/design-image-effects.cjs`（15 项，可选性 + 版本 + 渲染写法 + `withAlpha`
> 边界 + 变量图裁剪位置 + 源码静态核查，契约 I-44）；像素级证明在
> `test/design-export-e2e.cjs`（出真图读真像素：绿环在框内侧两侧各 1mm、框外透明、
> 投影投到框外、**半透明源图 ⇒ 阴影像素也半透明**——后者正是 `box-shadow` 做不到的）；
> 界面路径在 `test/design-e2e.cjs`（开关 → 画布 → 落盘版本 7 → 关掉要真删字段）。
- **预留 margin 随变换放大**：Compositor 的效果区随缩放/旋转同步留边，否则大投影被裁。
  对应到我们：裁切/缩放时效果外扩量要按比例换算。
- **效果可整组复制到其他图层**：给「复制效果」按钮，组内照片统一样式时省 N 次重复劳动。

### 7. JPEG/WebP 导出与质量控制 —— ✅ 已实现（2026-10-13）

> **落地结果**：`electron/export-formats.cjs` 是格式表唯一权威源（`FORMATS`：扩展名 /
> 透明能力 / 默认质量 / DPI 落法），`design-export.cjs` 与导出面板都读它（I-41）。
> 三种格式共用同一条 `renderDesign` 管线与同一次 CDP 截图，只是换 `format` / `quality`。
> 与下面建议的差异，都是落地时按真实约束改的：
> - **WebP 也做了**，不是「先只做 JPEG」——CDP 原生支持，成本几乎为零。
> - **WebP 不写 DPI**：没有公认的容器（塞 EXIF 也不是所有看图器认），如实不写并在界面说明，
>   比塞一个没人认的字段更诚实。
> - **JPEG 的 DPI 走 JFIF APP0 density**（不是 EXIF）：实现是「丢掉上游的 JFIF APP0、
>   在 SOI 之后补一个自己的」，于是无论编码器吐没吐 APP0，结果都恰好一个且密度正确。
> - **体积预估只给有损格式**：PNG 无损，体积由内容决定（矢量文字与照片能差几十倍），
>   `estimateOutputBytes` 对它返回 `null`；有损格式一律写「约」，导出完成后用**真实字节数**覆盖。
> - **透明取舍如实上报**：JPEG 勾了透明会改铺画布自己的底色（画布也是透明则退白），
>   用 `flattened` 报给界面提示，不静默丢层。
> - 守卫：`test/design-export.cjs`（I-41，24 项）+ 真实编码在 `test/design-export-e2e.cjs`（61 项）。

当前出图只有 PNG（还手工写 pHYs DPI）与 PDF 打印管线。S1 压测反复提到**体积**：
500 张大图的 PDF 两轮导出峰值约 1.9 GiB。建议：

- PNG 之外给 JPEG（质量滑杆 + 实时体积预估）与 WebP（更小，注意打印店环境兼容性，
  可先只做 JPEG）；
- 导出面板沿用 Compositor 的简化形态：质量、**是否铺底色**（transparent → flatten）、
  **DPI 元数据**（PNG 已有 pHYs；JPEG 需写 JFIF density/EXIF，别让 300dpi 设计
  导出去变 72dpi 默认值）；实时显示预估大小；
- 修 `design-export.cjs` 里只认 `.png` 的路径校验（`/\.png$/i`）为多格式白名单。

## 四、P2/P3：做不做看排期

- **PSD 导入（P2，全清单工程量最大的单件）**：Compositor 的 PSD 导入器把文件夹/文本/形状
  尽量保留为可编辑层，其余栅格化，**导入前给转换报告**；且明确能力边界：8-bit RGB only，
  超大 Photoshop 文件**把图层裁到画布而不是拒开**。对 PrintPress 的价值：用户手里大量既有
  底图是 Photoshop 做的。建议：评估现成解析库（如 `ag-psd`，纯 JS、离线可用）而非自研；
  只映射能映射的（图层图像、顺序、不透明度、简单文本），其余栅格化并在「转换报告」里
  逐条列明；复用 I-38 工程包已验证的「先校验后落盘、白名单条目、导入必是副本」范式。
- **命令面板（⌘F 搜命令）**：Compositor 是静态命令注册表 + SwiftUI 视图。
  PrintPress 已有 CustomSelect 等模式，做一个「命令表 + 快捷键 + 工具页全覆盖」的
  模糊搜索面板即可。功能数上去后这是可达性保险。
- **素材导入扩展 WebP/SVG**：SVG 需栅格化（建议右上有界 Raster 尺寸走 `nativeImage`，
  不引 sharp——与图片变量方案的约定一致）；WebP Chromium/Electron 原生可解码。
- **本地抠图（Remove Background）**：证件照换底是真实需求，但 RMBG 类模型 40–170MB、
  离线跑要 onnxruntime-node，与「零重依赖」取向冲突。列为观察项，等 S5 单人裁切
  做完、看用户真实使用数据再定。
- **快捷键自定义**：先固定一套合理快捷键（含方向键步长 Shift/Ctrl 分档），自定义后排。
- **agent 可读写的工程格式 + 外部变更确认**（P2，我方原低判，参照仓库启示后上调）：
  PrintPress 的工程已是 JSON 且 `api-cli` 有 86 个操作，增量只在两点——
  ① 工程结构对「脚本/agent 批量生成」显式友好（字段稳定、可无头写）；
  ② Compositor 的 `ProjectWatcher.swift`：工程目录被**外部写入/删除**时，
  弹「已变更，采用外部版本？保留我的？」而不是静默覆盖。批量出片本质是
  「一稿多变体」，这条把产能自动化做实。用 `fs.watch` + 确认对话框即可。
- **多工程标签 / 跨工程复制图层**（P3 观察项）：Compositor 靠单一文档协议直接跨窗拖图层。
  对「同一版式 N 个变体」是利器；但 PrintPress 的变体由「模板+数据集」驱动，重叠度高，
  等真实用户出现跨工程搬图层诉求再做。
- **更新提示纪律**：Compositor 把更新检查挂在 `whenReady` 之后且**不 await 首窗创建**。
  PrintPress 的启动检查同样应确保不阻塞首窗（I-35 场景是「点检查更新」，启动那次
  自动下载也别拖慢首屏）。

## 五、不建议搬的

| Compositor 能力 | 不搬的理由 |
| --- | --- |
| 选区、画笔、愈合、图章、液化、扭曲 | PrintPress 无像素编辑模型；版面工具已覆盖 |
| Camera Raw / Dither 等图像算法 | 打印底图用不上 RAW 工作流；Dither 半调属小众 |
| Remove Background 等 Vision AI | 依赖 Apple 框架，离线 Electron 只能换 ONNX 模型，体积代价大（见观察项） |
| 多标签多工程 | 任务流页面导航已覆盖诉求；仅作 P3 观察项（见上文），不主动做 |
| Photoshop 全套快捷键与可改键位 | 见上，固定一套即可 |

## 六、与 v0.6 路线图的衔接

- S1–S7（大批量、暂存恢复、增量补图、预检补打、单人裁切、表格、资源管理）不受本文影响；
- 建议把「比例裁切预设」并入 S5 单人裁切同一控件；
- S1 反复提到的输出体积，由「JPEG 导出 + 质量预估」承接；
- 本篇的 P0 三项（颜色调整/混合模式/滤镜 UX）体量小，可作为 v0.6 正式版后、v0.7 的第一批。
