# 图片变量与批量人像出片方案

> 编写日期：2026-10-09。当前基线 v0.4.0（底图图层工程、模板文本变量字段）。  
> 本文提出让**图片内容也随数据行变化**的能力，用于人物海报、员工墙、毕业纪念册、胸卡等场景。  
> 状态为待开发。标注「拟新增」「拟调整」的接口、函数与文件需要后续实现，不代表当前已经存在。  
> 与 [v0.5.0 开发计划](v0.5.0开发计划.md) 的关系：v0.5.0 的 M1「本地素材库」是本方案的天然前置（照片导入一次、多工程复用，缩略图与搜索对「从几千张照片里挑」也有用）。建议本方案作为 v0.6.0 交付，或借 v0.5.0 的素材库顺带完成 M1 部分。

## 一、目标与场景

**现状**：批量出片时底图（图片、文字、形状）**每页完全相同**；模板字段只支持**文本**，取值后经 `escapeHtml` 作为纯文本插入（`render-engine.cjs:307`）。也就是说，目前**没有任何途径让图片内容随数据行变化**。

**用户诉求**：让人物照片像字段一样逐行变化，背景保持一张固定底图——「一静一动」，批量产出人物海报。

交付后用户能做的事：

- 一张设计好的海报底图 + 一份名单（姓名、工号、照片文件名）→ 一次输出 N 页，每页同一背景、不同人像与姓名
- 人像框的位置、尺寸、裁切、圆角、旋转在底图编辑器里可视化调整
- 出片前拿到「第 N 行 张三 找不到 1001.jpg」这类明确的缺图报告，而不是打完才发现空框

| 优先级 | 功能           | 本版交付范围                       | 用户获得的能力                   |
| --- | ------------ | ---------------------------- | ------------------------- |
| P0  | 图片占位框图层      | 底图新增一种图层：几何完备、无具体图片，声明绑定到哪一列 | 海报里人像的位置与裁切可控             |
| P0  | 照片目录导入与文件名匹配 | 选择照片文件夹，按文件名与数据列配对，内容寻址入库    | 人事给一份 Excel + 一个照片文件夹即可开工 |
| P0  | 缺图/重复/坏图预检   | 出片前列出具体行与文件名，区分缺失、重复、格式不支持   | 「打完才发现空框」不再发生             |
| P1  | 人像自适应裁切      | 保持比例 + 裁切重心 + 圆角             | 不同尺寸的照片放进同一个框不变形          |
| P1  | 变量图按框尺寸优化    | 超出框所需像素的照片按目标 DPI 预缩放        | 500 人的作业不因体积崩掉            |
| 全程  | 与既有能力兼容      | 静态底图、文本字段、多联、对折、PDF 保真、归档快照  | 原有模板继续照常出片                |

**明确不做**：人脸检测与自动构图、抠图去背景、AI 修图、云端照片库、Excel 单元格内嵌图解析（列为后续版本）。

## 三、数据形态与匹配规则

### 3.1 三种取图方式

| 方式        | 数据形态               | 用户操作            | 优先级 |
| --------- | ------------------ | --------------- | --- |
| A 文件名匹配   | 一列存文件名（`1001.jpg`） | 选一个照片文件夹，系统按名配对 | P0  |
| B 直接拖一批照片 | 照片本身 + 按文件名/序号配对   | 拖入，自动生成或补齐对应列   | P1  |
| C 单元格内嵌图  | xlsx 里图片嵌在单元格      | 导入时抽取到素材库       | 后续  |

推荐 A 起步：最通用，且与现有 CSV/Excel 导入链路（`electron/importer/`）零冲突。人事给料就是这个形态。

### 3.2 文件名匹配规则（实战必踩）

数据里存的是**文件名**，必须归一化后再匹配，否则会「明明有图却报缺图」：

| 差异来源       | 现象                                    | 归一化做法                     |
| ---------- | ------------------------------------- | ------------------------- |
| 大小写        | Windows/macOS 默认不敏感，Linux 敏感          | 匹配键统一 `toLowerCase()`     |
| Unicode 形式 | macOS 上传的中文名是 NFD，Excel 里手打的是 NFC     | 匹配键统一 `.normalize('NFC')` |
| 扩展名        | `.jpg` / `.jpeg` / `.JPG`             | 视为同一格式，匹配键去扩展名            |
| 路径分隔符      | 数据里出现 `子目录/1001.jpg` 或 `子目录\1001.jpg` | 统一正斜杠后按**相对路径**解析         |
| 空白         | 前后空格、全角空格                             | `trim()` 后比较              |

**匹配键 = 去掉扩展名、NFC、小写的文件名**（如 `1001`）。这样数据里写 `1001`、`1001.jpg`、`1001.JPEG` 都能命中。

**冲突处理**：同一个键命中多个文件（`1001.jpg` 与 `1001.png` 同时在）→ **报错让用户删一个**，不静默选一个。

### 3.3 缺图预检

出片前必须给一份可执行的报告，复用现有「出口校验分级」（空值 / 超宽 / 重复行）的形态：

| 类别 | 判定                 | 处置                                  |
| -- | ------------------ | ----------------------------------- |
| 缺失 | 数据有值但目录里找不到文件      | 列出「第 N 行 张三 1001.jpg」；阻断，或按用户选择用占位图 |
| 空值 | 该列本来就没填            | 与现有空值同类，提示但不阻断                      |
| 重复 | 多行指向同一张照片          | 提示（多为复制粘贴出错，与现有重复行检测同源）             |
| 坏图 | 文件存在但不是有效 PNG/JPEG | 导入时用 `images.cjs` 嗅探拦下              |
| 超限 | 单张 > 64MB 或像素超限    | 导入时拦下，提示压缩                          |

## 四、安全边界（不可妥协）

本方案风险最高的一节。**图片路径来自用户的数据文件**，而数据文件可能来自第三方（人事发的 Excel、别人给的 CSV）。

### 4.1 数据里只允许「相对名」

- 数据列的值只当作**文件名**，不当作路径
- 解析后必须经 `resolveInsideDataDir`（`store.cjs:27`）收口到数据目录内的照片区
- 素材以内容寻址（sha256）入库，工程里存的是 `asset_<sha256>`，**数据里从不出现绝对路径**

### 4.2 明确拒绝的输入

| 输入                              | 拒绝理由         |
| ------------------------------- | ------------ |
| 绝对路径 `C:\Users\...\a.jpg`       | 任意文件读取       |
| 盘符 / UNC `\\server\share\a.jpg` | 网络请求、卡顿、内网探测 |
| `..` 越界 `../../../Windows/...`  | 目录穿越         |
| `data:` / `http:` / `file:` 前缀  | 远程加载、协议注入    |
| 空字节、控制字符、超长名                    | 路径解析歧义       |
| 符号链接指向目录外                       | 绕过路径校验       |

以上一律**在导入阶段**拒绝并记入报告，而不是等到渲染时才失败。

### 4.3 为什么「内联」让越界后果更严重

`inlineUrl`（`render-engine.cjs:52-56`）会把媒体文件 base64 内联进 HTML，而这份 HTML 会写入归档快照（`archive/年-月/<jobId>/snapshot.html`）并在系统浏览器打开。一旦路径校验被绕过，**任意本地文件都会被复制进归档目录**（`C:\Users\x\.ssh\id_rsa` 也会变成一份可打开的 base64）。

所以路径收口必须在**入库时**完成，渲染阶段只认 `asset_<sha256>`——这与现有 `design-layout.cjs:76` 的素材路径正则完全一致。

## 五、底图占位框图层

### 5.1 为什么放在底图，而不是模板字段

模板字段只有 `x/y/fontSize/align` 这类文本属性，做不出人像框需要的几何。底图的 image 图层已经有完整几何（`design-layout.cjs:99-106`）：位置、尺寸、裁切（`crop` 百分比）、翻转、旋转、透明度。做成「占位框」后，海报排版、圆角头像、参考线吸附、分组**全部现成复用**。

### 5.2 图层模型（格式版本 3）

```js
const placeholderLayer = {
  id: 'layer_xxx',
  type: 'image',
  name: '人像',
  x: 20, y: 40, w: 40, h: 50,   // 毫米，与现有图层一致
  rotation: 0, opacity: 1, visible: true, locked: false,
  variable: true,                // 拟新增：本图层内容由数据行决定
  bindColumn: '照片',             // 拟新增：绑定到数据集的哪一列
  fit: 'cover',                  // 拟新增：cover 填满 / contain 完整显示
  align: { x: 0.5, y: 0.5 },     // 拟新增：裁切重心，0.5 = 居中
  radius: 0,                     // 拟新增：圆角 mm（圆形头像 = w / 2）
}
```

`design-layout.cjs:101` 现在对没有素材的图片图层直接抛「图片图层缺少素材」，需要放宽为：`variable === true` 时允许 `assetId` 为空，且**必须**提供 `bindColumn`；`variable !== true` 时保持原有强制校验不变（旧工程行为不变）。

版本号沿用 v0.5.0 计划里的 `resolveSchemaVersion` 思路：存在占位框或效果时取 `Math.max(version, 3)`；旧版本应用遇到版本 3 应明确提示升级，不降级保存。

### 5.3 裁切策略

- `cover`：按框比例裁切原图（默认），配合 `align` 决定裁哪一边
- `contain`：完整显示，不足处留空
- 默认 **cover + 居中**

**不做人脸自动构图**（需人脸检测，超出范围）。但 `align` 可调——人像重心通常偏上，用户能把裁切重心上移，这对头像框已经够用。

### 5.4 编辑器交互

- 工具栏新增「＋ 人像框」，落一个默认 40×50mm 的占位框
- 选中后右侧属性面板显示：绑定列（下拉选数据集的列）、填充方式、裁切重心、圆角
- 画布上占位框显示为**虚线框 + 列名水印**，与真实图片图层视觉区分
- 未绑定列的占位框在保存时提示（不能出片）

## 六、渲染链路改造

### 6.1 静态部分复用 + 动态槽

现在 `prepareTemplateDesign` 把底图渲染成**一个字符串**、所有页共用（`render-engine.cjs:181-197`）。加占位框后必须拆开：

```js
// 拟调整：renderDesign 把动态图层渲染成「不含图片的槽」，静态部分仍可整块复用
const rendered = renderDesign(design, {
  classPrefix: 'print-design',
  fontFamily: normalizeFamily,
  assetUrl: (asset) => inlineDataUri(asset),
  slotFor: (layer) => `<div class="pp-slot" data-slot="${layer.id}" style="${slotGeometry(layer)}"></div>`,
})
// rendered.html  = 静态部分（仍只渲染一次）
// rendered.slots = [{ id, column, geometry }]（每页按记录填 URL）
```

`buildHtml` 的 `fieldsHtml(rec)` 变为：静态 html + 每个槽按 `rec[slot.column]` 解析出照片 URL 填入 + 文本字段。

**关键**：静态部分仍然只渲染一次，只有槽的 URL 每行不同——这样大底图的去重机制（同一张图不重复编码）不受影响。

### 6.2 批量体积与分批渲染

这是本方案**最容易被低估、也最会翻车**的约束。

现状：120 页批量 PDF 很轻松，因为底图内联**一次**。人像场景下每页照片不同，若照旧内联：

```
500 人 × 2 MB 照片 × 1.33(base64) ≈ 1.3 GB 单份 HTML
```

而 `printer.loadHtmlOnce`（`printer.cjs:37`）走 `loadURL('data:text/html,...')`，这个体积必然崩。三层解法：

**(a) 照片不进 HTML，改走 `file://` + `pp://`**

`loadHtmlOnce` 已有 `file://` 后备路径（`printer.cjs:41-44`）。当 HTML 超过阈值（建议 8MB）或模板含变量图时**主动**写临时文件走 `file://`，照片用 `pp://media/...` 引用（`main.cjs:50-56` 已注册该协议，`file://` 页面可正常请求）。这样 HTML 大小与照片数量**解耦**。

> **M0 必须实测**：`file://` 页面下 CSS `background-image: url('pp://...')` 在**打印用的 offscreen 窗口**里是否可靠加载。e2e 里 `loadFile(dist/index.html)` + `pp://` 已验证可用（`design-e2e.cjs:51-58`），但打印窗口场景要单独验。

**(b) 变量图按框尺寸预缩放**

人像框通常 30×50mm，300 DPI 只需 354×591 px；用户给的却常是 4000×3000 的 12MP 照片。**超出框所需像素的部分，打印时本来就用不上。**

```js
// 拟新增：用 Electron 内置 nativeImage 缩放，不引入 sharp 等原生依赖
function fitPhotoForSlot(buffer, slot, targetDpi, safety = 1.5) {
  const needW = Math.ceil(slot.w / 25.4 * targetDpi * safety)
  const needH = Math.ceil(slot.h / 25.4 * targetDpi * safety)
  const img = nativeImage.createFromBuffer(buffer)
  const { width, height } = img.getSize()
  if (width <= needW && height <= needH) return buffer          // 本来就够小，原样用
  const scale = Math.min(needW / width, needH / height)
  return img.resize({ width: Math.round(width * scale), quality: 'best' }).toJPEG(92)
}
```

- 放在**渲染准备阶段**（`print.cjs` / `printer.cjs` 层，可用 electron），**不放领域层**——领域层零 electron 依赖是项目铁律
- 原图字节**保留在素材库**，以后换成更大的框仍可用
- 需向用户说明：「人像已按实际打印尺寸优化，清晰度不受影响」

> **需产品确认**：这一步改变了「原图逐像素无损」的既有承诺（I-20，守卫 `test/bg-fidelity.cjs`）。建议明确区分：**底图素材保持无损**（内联一次，成本可接受），**变量图按框优化**（N 份，必须控体积）。若不做预缩放，就只能依赖 (a) 外链，体积压力会全部压到磁盘 IO 上。

**(c) 分批渲染**

即使预缩放后（约 80KB/张），500 人仍有约 40MB，建议分批：

- 每批 N 页（按体积估算，如 100 页或 20MB 上限，取先到者）
- 每批一份 HTML → `printToPDF` → 合并
- 合并 PDF 需要新增能力

> **M0 技术验证项**：PDF 合并方案——是引入合并依赖，还是改为「分批导出多个 PDF」或「分批直打」。此项决定 M3 的形态。

### 6.3 归档快照的自包含取舍

`render-engine.cjs:20-27` 的注释明确：快照要能在**系统默认浏览器**打开，所以必须自包含（内联）。但变量图场景下内联 N 张照片体积不可接受。

建议三选一，**在 M0 用真实数据量测后确定**：

1. 快照仍内联，但**限制页数**（如最多 20 页）
2. 快照内联**降质版本**（缩略图尺寸），并标注「归档预览」
3. 快照给出说明「照片未内联，完整内容需在本机数据目录查看」

## 八、开发顺序与阶段出口

## 九、验收清单

| 类别 | 必测场景                                 | 判定标准                 |
| -- | ------------------------------------ | -------------------- |
| 匹配 | 大小写、中文 NFD/NFC、`.jpg/.jpeg`、子目录、前后空格 | 能命中的不报缺图；同名冲突明确报错    |
| 缺图 | 缺失、空值、重复、坏图、超限                       | 出片前给出具体行号与文件名；不静默出空框 |


| 安全 | 绝对路径、盘符、UNC、`..` 越界、`data:/http:`、符号链接 | 导入阶段拒绝；渲染阶段只认 `asset_<sha256>` |  
| 几何 | 占位框位置、裁切、cover/contain、圆角、旋转 | 预览与 PDF 坐标一致（沿用现有毫米容差） |  
| 保真 | 大照片、透明 PNG、中文、人像与文字重叠 | PDF 保留照片码流（或按框优化后的码流）；文字可选取 |  
| 体积 | 500 行 × 2MB 照片 | 不 OOM；HTML 大小与照片数解耦；分批出片完整 |  
| 兼容 | v1/v2 静态底图、文本字段、多联、对折、120 页 PDF | 既有行为与当前回归基线不变 |  
| 归档 | 快照在系统浏览器打开 | 内容可读（或明确说明照片未内联） |  
| 实际安装包 | 真实 exe 完成一次 500 人出片 | 不能只在测试窗口通过 |

拟新增领域测试 `test/photo-match.cjs`、`test/design-placeholder.cjs`，扩展 `test:design-e2e`、`test:design-export-e2e` 与批量 PDF 回归。新增静态守卫需按 `docs/不变量契约.md` 登记新编号。
