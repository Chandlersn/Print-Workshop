# 批量成品的核对与重出

## 这个 skill 解决什么问题

批量产出的成品，交付后几乎必然会有「某个人某一项写错了，只重出这一张」的请求。这类请求看起来是最简单的工作——改数据、重出、结束——实际上是最容易出错的一类：

- 改错了字段（两个字段名长得像，取错了列）
- 改了源文件却没同步进中间数据集，重出的图和旧图一模一样
- 同步了但比对规则本身是错的，于是永远报「没有差异」
- 生成出来了，但成品上的字在一屏能看全的尺度下根本分辨不出对错
- 把过时的备份当成成品，或把可用成品当成垃圾清掉

这些错误的共同点：**每一步单独看都做对了，链起来却交付了错的东西**。本 skill 是一套把这类错误挡在交付之前的纪律，附一次完整事故复盘作为取证样本。

## 什么时候用

- 用户报「某某的某字段改了，重出」——无论他有没有给编号、单位、改成了什么
- 要批量生成几十到几千份带个人数据的成品
- 需要核对「已产出的成品」与「源名单」是否一致
- 成品与预期不符，要判定是数据问题还是渲染问题
- 手上有一批中间数据和一个用户维护的源表，两者可能已经不同步

## 接手前提：模板由人做好，且已成功导出过一小批

**这条是硬前提，不满足就不要开始批量。** agent 的职责是「按已经验证过的模板 + 已经审核过的名单批量生产」，不是从零设计版式。

开工前必须确认三件事，缺一件就要先补：

| 前提 | 怎么确认 | 缺了怎么办 |
|---|---|---|
| 用户在系统里**做好并保存了模板**（底图、字段位置、字号、对齐都定稿） | 模板 id 能查到，`ppw verify` 能读到它的 `fields[].column` | 请用户先在设计器里做好并保存——版式是审美与业务决策，agent 不替他定 |
| 用户**亲自导出过一小批**（1～3 张），并亲眼看过成品没问题 | 让用户指出这几张的文件名或目录 | 先出 1～3 张给用户确认，确认后再批量 |
| 数据目录可读、模板与名册能对上 | `ppw status` 报数据目录 / 名册 / 成品数量；`ppw verify` 无 error | 按报错补数据目录或改配置，不要猜路径 |

为什么必须先跑通一小批：模板问题（字段取错列、字号溢出、底图位置偏了）在单张上看是微调，在几百张上就是整批返工。**自动化只会放大模板的问题，不会修正它。**

这一小批同时是最好的验收样本：后面每次重出，都可以拿它当「渲染是否仍然一致」的基准——同一份数据重出，字节应当完全相同。

模板还没定稿时不要开工，也不要顺手改用户的模板：改模板会改变所有后续成品的排版，属于用户决策。

## 第一原则：成品读的是中间数据集，不是用户的源文件

批量出片读的是系统里的**数据集副本**。用户改 Excel 原件，系统不知道，必须显式同步。

由此推出两条操作约束：

1. **改完源表必须同步，否则重出的成品与旧成品逐字节相同。** 这是最容易让人误判「工具坏了」的一步。
2. **重出后如果 MD5 与旧图相同时，先怀疑没同步，不要先怀疑渲染。** 同样的输入必然产生同样的字节，这恰恰证明系统是确定的。

## 五条铁律

### 一、「零差异」不等于「数据干净」

差异比对只能证明**被比较过的字段**没有差异。当字段匹配规则本身错了（例如用「表头包含某关键词」去匹配，而表里有两列都命中），被比较的其实是另一列，真实字段从未参与比对，此时差异恒为 0。

因此：**任何比对规则改动之后，必须重看一次差异数字有没有跳变。** 数字一直是 0 不代表稳定，可能代表这个字段从来没被读过。

排查手法：把「已知口径/豁免规则」的命中数单独打出来。如果豁免命中的是几千行而真实差异是 0，几乎可以确定匹配规则吃错了列——正常的豁免应该是零星几条。

### 二、「用户说改了要重出」是取证请求，不是复述请求

用户说「我改了」，而系统里看不到差异时，**不要回「我这边没差别」**——那等于把举证责任推回去，双方各说各话。

要同时回答三件事：

| 要回答 | 怎么查 |
|---|---|
| 磁盘上的源文件是什么版本 | 文件修改时间（只到上次保存，这是 Windows/macOS 的固有盲区） |
| 文件是不是还被编辑器占用 | 同目录的锁文件（Excel/WPS 的 `~$<同名>`） |
| 差异具体是什么 | 逐字段比对，给出「源表值 / 数据集值」两侧 |

如果文件被占用，直接提示「磁盘内容是上次保存的版本，屏幕上的改动还没落盘，按 Ctrl+S 后我立刻重跑」。如果已保存，比对会自己把差异找出来——**不需要用户描述改成了什么**。

### 三、重出前先定位差异，不要凭用户描述改

用户报的是意图（「指导老师改了」），差异扫描给的是事实（哪一行哪一列、从什么改到什么）。

永远先跑差异扫描：它 1-2 秒能扫完全量几千行，同时完成三件事——定位是哪一条、确认源表是否真的保存了、证明差异只有这一处（而不是用户以为的一处）。**用户没给编号和单位时不必追问，全量扫描会自己定位到人和单位。**

只有当扫描结果与用户描述矛盾时（例如用户说只改了奖励等级，扫描却显示学校也变了），才需要回头确认。

### 四、重出的幂等性是免费的正确性信号

同一份数据重出两次，字节应完全相同。这条性质可以低成本地验证整条链路：

- 重出后与旧图 MD5 相同 → 输入没变。要么本来就没差异，要么同步失败了。
- 重出后 MD5 不同 → 输入确实变了，改动生效了。

比「看一眼觉得对」可靠得多，也比读日志可靠。

### 五、不擅自改用户的源表

发现源表自相矛盾（两个字段记同一件事却对不上）、或用户改完少了一个后缀（学校名丢了「分园」）时，**先指出，等确认**。

模板可能只渲染其中一个字段，另一列不一致不影响成品——但那是用户的台账，不是你的。指出来的成本是一句话，改错的成本是用户以后按错数据统计。

## 标准工作流：改字段 → 重出

```
1. 定位   全量扫差异，拿到「哪一行 / 哪一列 / 两侧的值」
2. 同步   把源表的值写进数据集，回读确认写入生效
3. 重出   只出这一张，旧成品挪进备份目录（不要覆盖）
4. 核验   目视核对关键字段 + 差异扫描归零
```

四条缺一不可。跳过第 1 步会改错人，跳过第 2 步会出旧图，跳过第 3 步的备份会丢原件，跳过第 4 步不知道做没做对。

批量重出多条时用一次批量调用（串行处理），不要循环调用单条接口——每次调用都要重连宿主，时间成本是数量级的差别。

## 三个高频故障

详细复盘见 [references/failure-modes.md](references/failure-modes.md)。

| 症状 | 大概率原因 | 排查 |
|---|---|---|
| 重出的成品和旧的一模一样 | 改了源表但没同步进数据集 | 比对数据集字段与源表字段 |
| 差异扫描一直报「0 处」，但用户坚持改了 | 字段匹配规则吃错了兄弟列，该字段从未被比较 | 打印豁免规则命中数，几千行即异常 |
| 用户说改了，系统看不到任何差异 | 文件被编辑器占用，改动还在内存里没落盘 | 查 `~$` 锁文件与文件修改时间 |

第四个故障不在数据层而在感知层：**成品上的字看不清**。见下一节。

## 字段清单是算出来的，不是写死的

任何「必填字段有几个、分别叫什么」的说法都只是**当前批次的快照**。字段集合在运行期由三处共同决定：

| 真源 | 决定什么 | 在哪 |
|---|---|---|
| 模板 `fields[].column` | 成品真正渲染哪些字段——出口校验用的就是它 | 数据目录 `templates.json` 里本批模板 |
| 必填清单配置 | 每个字段**怎么从源表头认出来**（`eq:` / `prefix:` / `contains:`），以及额外的业务必填 | 批处理配置的 `requiredFields` |
| 数据集 `columns[].printOn` | 哪些列在界面上「点亮」 | 数据集每一列的开关 |

批处理工具的做法是**以模板为准**：模板这次声明 8 个字段就校验 8 个，下次改成 5 个或 9 个自动跟着变；配置只补匹配规则，没配到的列退化成「精确同名」匹配。所以换一批字段数量不同的名单，只需要改模板和匹配规则——**不需要改代码，也不需要改这份文档**。

拿到任务时按这个顺序确认真实清单，不要凭印象：

```bash
node tools/ppw.cjs verify        # 打印「模板渲染 N 个字段 / 必填清单 M 个字段」并列出名字
```

- 模板有、清单没有 → 下次导入不会点亮该列（warn）
- 清单有、模板没有 → 多校验一次，无害（info）
- 数据集里**列根本不存在** → 成品该位置必然空白（error）

想验证某个字段到底有没有被真正读到（而不是被兄弟列冒名顶替）：把它临时改成一个可辨识的值，重出一张，看成品上出现的是不是它。比读代码快，也比读注释可信——`contains:` 抢错列那次，代码和注释看起来都是对的。

## 字段没点亮：第三个静默缺口

数据集里每一列都有一个「印」开关（`printOn`）。它不是出片闸门，而是**绑定的前提**：

- 它**控制**：模板编辑页能不能选到这一列、模板换绑数据集时算不算结构错配、打印预检要不要报警
- 它**不控制**：已配好模板的直接出片（渲染读的是行里的值，不看开关）

所以它造成的故障是延迟发生的：导入时没点亮 → 当下出片正常 → 几个月后要改模板，发现那个字段选不到，或者换绑时莫名其妙判成结构错配。

**脆点在两份清单的对齐**：导入时按配置里的「必填字段清单」点亮，而模板要渲染哪些字段由模板自己声明。模板后来加了一个字段、没人记得往清单里补，这一列就是暗的，且不报任何错。

```bash
node tools/ppw.cjs verify              # 校验模板字段 ↔ 必填清单 ↔ 数据集开关 三者是否对齐
node tools/ppw.cjs verify --unit 55    # 单个单位
```

判定分级：列**不存在** → error（出片真空白）；列在但**未点亮** → warn（影响改模板 / 换绑，不影响已出片）；模板要的列**不在必填清单** → warn（下次导入不会点亮）。

**新导入一批名册后、改过模板字段后、换绑数据集之前，都要跑一次。**

完整口径（含「注释说会空白、实测不会」这条冲突的处理）见 [references/print-on-switch.md](references/print-on-switch.md)。

## 形近字：核对分辨率决定核对结论

成品图通常是 A4 300dpi（2481×3508）。缩到一屏能看全时，`钥/玥`、`街/节`、`梓/锌` 这类只差一个偏旁的字**在物理上不可分辨**——不是容易看错，是没有足够像素。

而批量数据里最高频的错误恰恰就是一字之差：姓名同音字、学校名错别字、指导老师姓名。「我看过了没问题」和「我其实看不清」之间，必须有明确的界线。

做法：把待核对的那一行裁出来放大再看，且**放大只能用最近邻**——双线性插值会把偏旁插糊，正好毁掉唯一要看的那点笔画。

```bash
node tools/png-crop.cjs <源图> <输出图> [x y w h] [放大倍数]
```

省略坐标时用的是**本仓库当前模板版式**的默认位置（2481×3508 的证书，对准「就读学校 / 指导教师」两行）。换模板、换输出尺寸时必须显式给坐标——默认值只对这套版式成立。这两个字段是错字的常客，值得优先设成默认。

## 备份目录的语义

`_partial_backup/` 这类目录里的文件有两种截然不同的身份，不能一概处理：

- **可用成品**：上次批量出片时留下的，内容正确且完整 → 可以当作「已出」认下来
- **过时旧版**：重出前挪走的，内容已明确被取代 → 绝不能当作「已出」

区分线索通常是文件名后缀（如 `_改前`）。默认策略应当是**不采信备份目录**，单独计数并提示，确认可用后再显式认它。把过时的旧版当成已出，是最难发现的错误——对账全绿，成品是错的。

## 参考实现：批印坊 ppw

本仓库内 `npm run ppw -- <命令>` 提供十个命令，完整参数与输出格式见 [references/ppw-commands.md](references/ppw-commands.md)。三层对账的口径（名册×磁盘、名册×字段、名册×数据集）见 [references/reconciliation-model.md](references/reconciliation-model.md)。

最常用的三条：

```bash
npm run ppw -- status              # 开工前自检：数据目录、名册可读性、锁文件
npm run ppw -- drift --all         # 全量扫源表与数据集的差异（最快、最常用）
npm run ppw -- fix --sheet "55_某单位" --name "某某" --set "<字段名>=<新值>"
```

`--set` 里的字段名取当前批次必填清单里的名字（`ppw verify` 会打印，示例中的名字只是举例，不保证下一批还有这一列）。

`fix` 不带 `--set` 就是「不改数据、把这一张重印一次」，用于视觉异常而非数据异常。

注意：ppw 需要在本仓库根目录运行，它会自行 spawn 宿主进程，不需要手动启动 Electron，也不用手动清理 `ELECTRON_RUN_AS_NODE`。

## 落地检查清单

交付前逐条确认：

- [ ] 差异扫描归零，且豁免规则命中数与改动前一致（跳变说明规则吃错了列）
- [ ] 每个张重出的成品都目视核对过，形近字用裁剪放大看过
- [ ] 模板字段 ↔ 必填清单 ↔ 数据集「印」开关三者对齐（`ppw verify` 无 error）
- [ ] 旧成品在备份目录里，原件没被覆盖
- [ ] 数据集回读确认过，不是只信写入返回值
- [ ] 与源表自相矛盾的地方已向用户指出，没有擅自改源表
- [ ] 剩下的缺口（缺字段、编号为空、等用户补数据）已明确列出，而不是被静默跳过
- [ ] 字段集合按 `ppw verify` 的实际输出处理，没有假设「这批一定是 8 个 / 一定有某个列名」
